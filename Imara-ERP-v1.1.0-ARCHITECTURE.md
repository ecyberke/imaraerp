# Imara ERP — v1.1.0 Implementation Architecture

**Status:** draft for approval (rev. 2 — aligned with Forge 2.1.0 release, brownfield and scaffold rules) · **Baseline:** v1.0 = `main` + PRs #18, #19, #20 (commit `a961cb0`, branch `etims-integration`) · **Governed by:** AI Web App Forge 2.1.0, brownfield mode, proposed risk class **R4**

## How this document relates to the others

There are three sources of truth from v1.1.0 onward, and each one owns something different.

- **`Imara-ERP-ARCHITECTURE.md` (v21)** stays authoritative for the domain: entities, posting rules (§7), state machines, Kenyan compliance logic. v1.1.0 adds no new business domain and does not restate it. It changes only what ADRs say it changes (ADR-002 and ADR-007).
- **`.forge/*.yaml`** is authoritative for requirements (`REQ-*`/`NFR-*`), specs, tasks, invariants, authorization policies, threats, tests and gates. Forge enforces those links with `forge validate` instead of relying on discipline.
- **This document** explains *why*: the comparison against Forge, the design changes, and the decisions that need you. Wherever it mentions an artifact, it gives the ID rather than repeating the content. **Appendix A is generated by `forge render architecture`.** If Appendix A and the YAML ever disagree, the YAML wins and the appendix is re-rendered.

This replaces v1.0's doc-as-code policy ("a PR that changes a modeled entity updates the architecture doc") with a stronger one. A PR that changes behaviour updates the `.forge` artifact it touches, `forge validate` must exit 0 in CI, and views are re-rendered.

## 1. What v1.1.0 is, and is not

v1.1.0 is a **hardening and verifiability release**. v1.0 is functionally broad: twelve modules and a real double-entry ledger, backed by 243 passing PHPUnit tests. But what "verified" meant in v1.0 was "its own PHPUnit suite passes", and Forge asks for much more than that at Imara's risk level. v1.1.0 does five things.

1. It lands v1.0's three open PRs safely, with eTIMS behind a default-off flag.
2. It puts the codebase under Forge governance so every claim maps to evidence.
3. It closes the security and reliability gaps those new gates expose.
4. It measures performance against the §1.1 targets for the first time.
5. It closes three functional holes: PO cancellation, subcontract settle/dispute, and module dashboards.

**Out of scope** (unchanged from v21 §14 backlog): full banking, multi-currency revaluation, custom roles, WMS/MRP depth, HSE, tendering, document control, statutory online filing. The PWA offline mode for site supervisors also stays deferred.

## 3. Governance model

**Risk class R4 (proposed, ADR-001).** Imara posts a double-entry ledger, runs payroll on employee PII, collects money and will submit tax invoices. That is the "financial" class in Forge's risk table. In practice R4 means four things:

- **Required gates on IMPLEMENTED → VERIFIED:** build, typecheck, lint, unit, integration, contract, e2e, security, runtime, self_audit, accessibility, performance, reliability, adversarial.
- **No project-wide waivers:** a security, e2e, runtime, reliability or adversarial gate can only be skipped by an exception scoped to one release candidate, with an expiry.
- **Self-audit categories that can never be marked not-applicable:** Security, Authorization, Data integrity, Concurrency, Idempotency, Secrets, Dependencies and Adversarial scenarios.
- **Optional but recommended:** `persistence` and `clean_room`. They are opted into through `runtime.yaml` and deliberately *not* declared as `true` commands, since a fake gate is worse than none.

**Ownership** follows Forge's model, and the v1.0 convention that **no branch is ever merged autonomously** is kept unchanged.

- `project.yaml` and `.forge/decisions/` are yours. The `project.yaml` delivered here is a draft for your approval.
- Requirements, specs, tasks, domain and verification files are shared between you and Forge.
- State, manifest, evidence and views are written only by Forge.

**What R4 does not give you.** Forge says plainly that R4 adds those two rules and nothing else. There is no independent security review, no enforced segregation of duties, no chaos testing. Imara's maker-checker is application logic (INV-009), not a Forge workflow. Because Imara holds money and payroll, v1.1.0 adds an external penetration test as an explicit human task (TASK-194, recorded through `forge accept ACC-008`).

**Maturity path for this brownfield baseline.** `forge init` starts at PLANNED even though v1.0 already runs, and two human gates follow:
- **PLANNED → SPECIFIED:** when you approve the constitution and ADRs (TASK-103).
- **SPECIFIED → IMPLEMENTED:** when the non-blocked Phase 1–5 tasks are done.

From IMPLEMENTED onward every transition is gate-enforced: application, then staging, then production approval with your sign-off, then production. The exception is PRODUCTION_APPROVED → PRODUCTION_DEPLOYED, which is a third human gate.

**How a human gate is passed — tested, not assumed.** Forge 2.1.0 has no approve command, and `forge advance` exits 3 at a human gate. The only path is the audited one:
1. **You** (never Claude — the skill forbids it writing `state.yaml`) change `maturity.state` in `.forge/state.yaml` to the next state.
2. Run `forge state reset-integrity --by "<name>" --reason "<what was approved>"`.
3. Commit with that reason in the message.

In a throwaway copy, `forge sync` refused the hand edit with exit 4 until `reset-integrity` was run, and `forge validate` then passed. `reset-integrity` only *prints* who and why; it stores neither. The commit message is therefore the approval record.

**What "done" means in v1.1.0.** A task is done when its own test passes. A release is VERIFIED only when `forge advance` says so — every required gate passed on one release candidate, with evidence under `.forge/evidence/`. "It works" is never reported from output alone.

## 4. Design changes by area

Each item below is design intent only. The authoritative detail sits in the referenced IDs.

### 4.1 Tenancy kernel (COMP-004, SPEC-015)
v1.0 resolves the tenant from the authenticated user on every query. That is correct for HTTP requests and undefined for everything else. v1.1.0 adds an explicit `TenantContext` set by request middleware, by job middleware (every job carries `tenant_id`), and by a per-tenant fan-out for scheduled commands. A tenant-scoped query with no context **throws** instead of guessing (INV-017, TEST-037). A lint step blocks `withoutGlobalScopes()` outside an allowlist. Cache keys carry the tenant prefix.

ADR-003 then adds Postgres row-level security as a second layer, so a missed scope fails closed at the database. It is optional and needs your approval.

### 4.2 Identity and authorization (COMP-002, COMP-003)
The nine-role matrix is declared once as POLICY-001..015. The authorization test is *generated* from it. For every action and role it checks allow, deny, other-tenant (404) and unauthenticated (401).

The role mappings were reconstructed from §11 and the User Manual. TASK-113 compares them with the real Policy classes, and any disagreement becomes a decision for you, never an edit that makes a test pass.

Finance is explicitly denied payslips and salary-bearing audit rows (POLICY-004/005). The audit-log rule is a row filter, which the Forge schema can't express, so SEC-TEST-003 owns it. Token lifecycle work is covered by ADR-005, and the MFA route sweep (SEC-TEST-012) proves no mutating route escapes the `mfa` middleware.

### 4.3 Ledger integrity (COMP-005, ADR-004)
Reversal-only stops being a convention and becomes physically enforced. Database triggers reject UPDATE/DELETE on posted journal rows and audit rows. A deferred constraint rejects any entry whose debits and credits differ at commit. TEST-051 adds a property test: random valid posting sequences must always leave the trial balance at zero. It complements the 65 example-based posting tests.

### 4.4 M-Pesa trust model (COMP-009, ADR-002)

```
Invoice ──► STK request committed (pending_external) ──► Daraja STK Push
                                                            │
  callback /webhooks/mpesa/stk/{hmac-token}  ◄──────────────┘ (unsigned)
      │ token ok? IP allow-listed? CheckoutRequestID matches a pending row?
      ▼  stored as a claim only (status: confirming)
  Daraja STK Query ──► ResultCode 0, amount and MSISDN match? ──► Payment posted once
      ▲                                        (unique CheckoutRequestID and receipt no.)
  Reconciliation job: any request pending > 3 min is queried; expired at 24 h
```

This supersedes v21 §1.1's HMAC-plus-nonce promise, which Safaricom cannot meet. With this design, a forged callback can do no more than trigger a status query.

### 4.5 Integration runtime (COMP-008, REQ-041)
Every external side effect becomes an `OutboxMessage` written inside the same transaction as the business change. Workers send it through a client with an explicit timeout and a per-provider circuit breaker. Failures retry with jittered backoff and dead-letter into a Notification.

STK initiation is the one exception: it is not idempotent, so it is never retried automatically. Per-tenant feature flags (REQ-045) gate every adapter, and eTIMS and M-Pesa ship disabled until their sandbox acceptance checks (ACC-003, ACC-004) are recorded.

### 4.6 Uploads (COMP-011, REQ-035)
BOQ imports and compliance documents share one pipeline:
- content-type sniffing against an allowlist;
- size and row caps;
- PhpSpreadsheet in read-data-only mode with external entities disabled;
- a private bucket with UUID keys and signed-URL download;
- escaping of formula prefixes on re-export.

### 4.7 Data protection (REQ-040)
Kenya DPA subject requests are a maker-checker `DataSubjectRequest`. Employee PII is anonymised in place, while payslip amounts are kept as statutory records. Audit identities are anonymised through a dedicated database function, consistent with ADR-004. Tenant export and soft-delete with a retention window satisfy the multi_tenant module.

### 4.8 Performance (NFR-001)
Measure first, then fix:
- a volume seeder for a three-year reference tenant;
- query-count guards on every list endpoint;
- an index and EXPLAIN audit;
- k6 load tests against per-class budgets;
- a bundle budget for the SPA, since the Materialize full-version is heavy on Kenyan mobile networks.

Reports that miss the 2 s budget become queued jobs with a Notification, as §1.1 already intends.

### 4.9 Release and operations
Staging runs the *same* artifact as the application RC and is verified with `forge verify --profile staging --environment staging`. Each environment needs a written, rehearsed rollback plan before deploy (ADR-009, ADR-010).

Rollback means redeploying the previous artifact. That only works because every v1.1.0 migration is expand-only, and TASK-156 enforces it. M-Pesa and eTIMS can also be switched off per tenant without a redeploy. Restore-from-backup is for data loss, never for rollback.

PRODUCTION_VERIFIED also needs the operational handoff (TASK-193): runbooks for M-Pesa settlement drift, queue/outbox backlog and database failover.

### 4.10 Functional completion
- **PO cancel and short-close (ADR-007):** finally gives `Project.cancel()` something real to call for open POs.
- **Subcontract and progress-claim settle/dispute (REQ-039):** follows once cancellation exists.
- **Module dashboards (REQ-042):** for the five modules that have none today.
- **Live inventory board (REQ-046):** built only if the load test says it is needed.

## 7. Drift found between v1.0 documents and code

The comparison turned up these mismatches. They are recorded so they get corrected, not argued over again.

1. **Audit coverage.** v21 §3.10 says the audit observer was attached to every financial entity "from the start". It wasn't until PR #18. → TEST-036 now enforces it.
2. **Webhook security.** v21 §1.1 promises HMAC and nonce verification on webhooks; Daraja doesn't sign callbacks and the implementation uses an opaque ID. → ADR-002.
3. **Money assertions.** `execution_plan.md` says to use `assertEqualsWithDelta` for money, but money is integer cents. → ADR-008.
4. **README.** It is template boilerplate, which the handover explicitly warns about. → TASK-104 plus the `clean_room` check.
5. **Scaffold tests counted as coverage.** `ExampleTest` ("true is true") is included in the 243. → TASK-104.
6. **Payslip self-service.** v21 Imara-ERP-ARCHITECTURE.md:539 (§12 Open Decisions, item 9) promises employee self-service payslips, but no employee role exists. → ASM-011.
7. **Undated statement.** §1.1's performance targets were stated but never measured. → TASK-173.

**If your local copy is newer,** run `forge validate --strict` with it after adoption (execution plan, "Local setup"). Anything it reports is the authoritative list of what still needs to change.

**Commands run against these artifacts** (scratch repository; the Imara code wasn't available here):
- `forge validate --strict` → **exit 0**
- `forge capabilities resolve` → exit 0
- `forge render all` → exit 0, deterministic across runs
- `forge status` → stage **PLAN**, maturity **PLANNED**

In rev. 1, five deliberate breakages in a throwaway copy were all rejected by validation.

**Caveat:** `jsonschema` couldn't be installed offline, so schema checks ran through a local subset implementation covering every keyword Forge's schemas use. That is not the real library. Your first `forge validate` with the real library is the authoritative run.

**Findings that belong to Forge itself, not Imara,** worth adding to Forge's backlog:
1. `project.authentication.strategy` has no value for opaque bearer tokens (ASM-004).

6. **Human maturity gates have no command.** PLANNED→SPECIFIED, SPECIFIED→IMPLEMENTED and PRODUCTION_APPROVED→PRODUCTION_DEPLOYED can only be passed by hand-editing `state.yaml` plus `reset-integrity`, and its `--by`/`--reason` aren't persisted. ### System Context
Multi-tenant SaaS ERP for Kenyan construction contractors. A Vue 3 + Vuetify SPA (Materialize admin template) talks to a Laravel 12 / PHP 8.2 JSON API over HTTPS with Sanctum opaque bearer tokens. PostgreSQL is the only supported store and is load-bearing for correctness (SELECT ... FOR UPDATE, advisory locks, and from v1.1.0 triggers, deferred constraints and optional row-level security). A database queue and the Laravel scheduler run asynchronous and recurring work. External parties are Safaricom Daraja (STK Push collection, inbound unsigned callback), KRA eTIMS OSCU (tax device and invoice submission, outbound only), and TalkSasa (SMS). v1.1.0 adds no new business domain; it makes the v1.0 domain (Imara-ERP-ARCHITECTURE.md v21, unchanged as the domain source of truth) verifiable, closes security and reliability gaps, measures performance, and completes three functional holes.

### Security
- **abuse_rate_limiting**: Named limiters: login (5/min per account, 20/min per IP), api (120/min per user, 1,200/min per tenant), reports/exports (10/min per user), uploads (20/hour per user), STK push (3/min per invoice). All return 429 with Retry-After. Expensive reports beyond the p95 budget run as queued jobs with a completion Notification.
- **audit_logging**: Append-only AuditLog with actor, action, entity, old/new values, IP, correlation ID and timestamp on every money-bearing model, auth event and role/MFA change. Coverage is enforced by an architecture test, not by memory, and immutability by a PostgreSQL trigger. Salary-bearing rows are filtered from Finance.
- **authentication**: Sanctum opaque bearer tokens (pure bearer mode; statefulApi prohibited). Passwords bcrypt (Laravel default). Login limited per IP and per account with lockout. v1.1.0 adds absolute token expiry, idle timeout for Finance/Admin, logout-everywhere, TOTP replay protection, hashed one-time recovery codes and an audited, maker-checker MFA reset (ADR-005, ASM-002). MFA stays mandatory for Finance/Admin on mutating routes and a route sweep test proves no mutating route escapes the middleware.
- **authorization**: Server-side Policies are the only authority; CASL only shapes the UI. The matrix is declared once as POLICY-001..015 in domain.yaml and SEC-TEST-001 is generated from it, covering allow, deny, other-tenant (404) and unauthenticated (401) for every action. Payroll confidentiality (Finance never sees individual pay) and the audit-log row filter are tested explicitly. Role logic stays hard-coded per §11; custom roles remain backlog.
- **data_protection**: TLS 1.2+ with HSTS; database and bucket encrypted at rest in a Kenya/Africa region (NFR-006); backups inherit the same protection. Kenya DPA 2019 rights are implemented as DataSubjectRequest flows — employee PII anonymised in place, payslip amounts retained for statutory record keeping, audit identity anonymised not deleted, tenant export and soft-delete with a retention window (REQ-040).
- **dependency_risk**: composer.lock and package-lock.json committed; composer audit and npm audit fail the security gate on high or critical. Named single-maintainer risk: pragmarx/google2fa (authentication path) and PhpSpreadsheet (untrusted input path) — both pinned and on a monthly update cadence. The Materialize template's unused apps are removed to shrink the attack and bundle surface.
- **input_validation**: FormRequest validation at the API edge for type, range, length and format; quantities reject zero/negative except variation_type=omission; rates/amounts reject negatives; money accepted as decimal strings and converted once to integer cents. Uploads are content-sniffed, size- and row-capped, macro-stripped, parsed with external entities disabled; exported CSV/XLSX cells beginning with = + - @ are escaped.
- **secrets**: Platform secrets come from the host's secret store and are declared in contracts/environment.yaml. Provider credentials are per tenant, encrypted with APP_KEY, masked on read and never logged. v1.1.0 adds APP_KEY rotation (APP_PREVIOUS_KEYS plus a re-encrypt command), a Monolog redaction processor, scrubbing of retained raw provider responses (the eTIMS communication key is currently stored in raw form) and gitleaks in CI.
- **threat_model_ref**: THR-001, THR-002, THR-003, THR-004, THR-005, THR-006, THR-007, THR-008, THR-009, THR-010, THR-011, THR-012, THR-013
- **trust_boundaries**: Browser to API — every request authenticated, authorised per POLICY-*, validated by FormRequests at the boundary, Daraja to webhook — unsigned public endpoint; payload is a claim to be confirmed (THR-002, THR-003), API to Daraja/eTIMS/TalkSasa responses — parsed defensively, schema-checked, secrets scrubbed before persistence (THR-011), File upload — untrusted binary content (THR-006), Queue and scheduler — code running without an HTTP user must carry an explicit tenant (THR-012), Support/ops access to the database — audited bastion only (THR-010)

### Reliability
- **backup_restore**: Continuous WAL archiving with point-in-time recovery (RPO 15 min), daily base backups retained 35 days, monthly retained 12 months, encrypted, stored in a second in-region zone/provider; bucket versioning plus replication. RTO 4 h for regional loss. Restore drilled monthly into scratch and logged.
- **concurrency**: Pessimistic row locks for credit checks, stock reservations, milestone sign-off, BOQ-line VO mutation and document sequences; unique constraints for approvals, idempotency keys and M-Pesa receipts; optimistic version check between DLP job and manual closure; advisory lock on the first reservation for an item. Every one is an INV-* with a real-subprocess concurrency_test.
- **failure_modes**: Daraja timeout/5xx on initiation -> request failed, no retry, user may resend (initiation is not idempotent), Daraja callback lost -> reconciliation job runs STK Query after 3 min, expires at 24 h, Daraja 429 or breaker open -> STK disabled with a clear message; invoices still payable by other methods, eTIMS down -> invoice raised locally, submission waits in outbox, dead-letter Notification after retries, TalkSasa down -> in-app notification already committed; SMS dead-letters, Database unavailable -> /ready fails, load balancer drains, writes fail fast with 503, Queue worker crash mid-job -> job retried; idempotency keys and unique constraints prevent double effect, Scheduled job overrunning its interval -> withoutOverlapping/onOneServer skip plus overrun Notification
- **graceful_degradation**: Integrations are non-critical to every core flow: invoicing, approvals, payroll and reporting never wait on Daraja, eTIMS or SMS. Report generation over budget degrades to async with Notification.
- **idempotency**: Idempotency-Key header on every financial mutation with a unique (tenant, key) constraint and stored response; provider events deduplicated by unique CheckoutRequestID and receipt number; outbox keyed per provider operation; depreciation unique per asset and period.
- **migration_rollback**: Financial tables are additive-only (lint in CI). Every migration is expand/contract: add nullable, backfill in a job, then constrain in a later release. Large-table indexes use CREATE INDEX CONCURRENTLY in a non-transactional migration. Every migration ships a tested down() or a written forward-fix plan; restore-from-backup is never the rollback plan.
- **queues**: Database queue in v1.1.0 with failed_jobs as the dead-letter store surfaced as Notifications; every job carries tenant_id and correlation_id and re-validates its subject at execution. Redis becomes required when more than one app instance runs scheduled work (onOneServer needs a shared lock store).
- **recovery**: After any restore older than the newest posting, reconcile against external records (provider statements, notification log, client records) and re-post lost entries dated at recovery time; never backdate or rewrite. Exercised in the monthly drill (ACC-001) and the migration rehearsal (ACC-002).
- **retries**: Only idempotent calls are retried: exponential backoff 1s, 2s, 4s with plus or minus 25% jitter, max 3 attempts, total budget 30 s for request-path calls; outbox workers retry up to 6 times over about 1 hour, then dead-letter. STK initiation is never auto-retried.
- **timeouts**: DB statement_timeout 5 s on request connections (30 s on report/queue connections); cache 500 ms; Daraja 10 s; eTIMS 15 s; TalkSasa 30 s; upload processing 60 s (queued beyond that). Set explicitly on every client, never left to library defaults.
- **transactions**: Business change, its journal entry, its audit rows, its Notification record and any OutboxMessage commit in one transaction. External calls happen only after commit via the outbox, except STK initiation, which commits pending_external first and then calls out.

### Scalability
- **async_work**: Notification dispatch, all external calls (outbox), reports exceeding budget, BOQ parsing of large files, depreciation, DLP scans, assignment status advance, reorder checks, M-Pesa reconciliation — all queued or scheduled, each fanned out per tenant.
- **bottlenecks**: DocumentSequence row lock serialises numbering per tenant/type — accepted at target load, first to revisit, Stock reservation lock per item/warehouse on month-end bursts, Computed availability over stock_ledger past ~5M rows per tenant (materialised view, REQ-046), Materialize full-version bundle size on Kenyan mobile networks
- **caching**: Report results cached per tenant with keys prefixed tenant:{id}:report:{name}:{params-hash}, invalidated on any posting to that tenant's ledger (event-driven), TTL 10 min as a safety net. No HTTP caching of API responses (all private, Cache-Control no-store). Static SPA assets are content-hashed and cached immutably.
- **database_strategy**: Single PostgreSQL primary, shared schema with tenant_id on every tenant table. PgBouncer in transaction mode (RLS uses SET LOCAL so it is pool-safe). App pool 20 connections per instance against max_connections 200, leaving headroom for workers and the bastion. Read replica only when the availability board or reports need it.
- **expected_load**: Proposed (ASM-010, requires confirmation): 20 tenants, 25 concurrent users per tenant at peak, 30 rps sustained and 120 rps burst across the deployment; month-end and milestone days are the burst periods. A reference tenant holds 3 years of a mid-size contractor (~600k journal lines, ~250k stock_ledger rows).
- **horizontal_scaling**: API instances are stateless (bearer tokens in DB, uploads in object storage, cache shared), so they scale horizontally behind a load balancer. Scheduled jobs require onOneServer with a shared Redis lock before a second instance is added.
- **indexes**: Every foreign key (asserted by TEST-040), (tenant_id, status) and (tenant_id, posting_date) on invoices, progress_claims, journal_lines, (tenant_id, item_id, warehouse_id, created_at) on stock_ledger, (tenant_id, account_id, posting_date) on journal_lines for GL and trial balance, (status, next_attempt_at) on outbox_messages, unique (tenant_id, entity_type, fiscal_year) on document_sequences, unique (tenant_id, checkout_request_id) and (tenant_id, mpesa_receipt_number) on mpesa_stk_requests / payments
- **performance_budgets**: p95 simple read 300 ms, p95 write including ledger posting 800 ms, p95 §10.1 report 2 s at reference volume, error rate under 1%, SPA initial load under 3 s on throttled 4G (Lighthouse mobile), initial JS under 350 KB gzip. Enforced by the performance dimension (k6 thresholds, query-count tests, EXPLAIN check, bundle check).
