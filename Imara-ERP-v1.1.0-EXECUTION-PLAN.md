## Working conventions (kept from v1.0, tightened by Forge)

- One branch per task (or a tight group sharing a spec), PR before merge, **no autonomous merges — ever.** Stacked branches target their predecessor until the chain is ready, as with #18 → #19 → #20.
- Every PR names its `TASK-*` and updates any `.forge` artifact its change affects. CI runs `forge validate --strict` and fails the PR on a nonzero exit.
- `forge validate` rejects a task marked `in_progress`, `review` or `done` while any `depends_on` task isn't `done`.
- **Verification tampering is never acceptable** (exit 4):
  - weakening an assertion, skipping a test, or widening a timeout to hide a hang;
  - adding a delta tolerance to a money assertion (ADR-008);
  - mocking the thing a test exists to exercise.
- **Two v1.0 testing traps** apply to every new test written in this plan:
  - **Real-subprocess concurrency tests** (TASK-116..119 and anything touched by TASK-134/136) disable transaction wrapping, so they must clean up manually in `tearDown()` in foreign-key order. Use the role-gated session flag for ADR-004's triggers; never disable a trigger in app code.
  - **Multi-identity tests** (all of SEC-TEST-001) must call `$this->app['auth']->forgetGuards()` before each identity switch, and again after any tenant-scoped query in between.
- **Known issues are recorded, never fixed silently.** Each KI-* in `baselines/inventory.yaml` points to the task that resolves it.

## Passing a human gate

Three maturity transitions have no verification profile: **PLANNED → SPECIFIED**, **SPECIFIED → IMPLEMENTED** and **PRODUCTION_APPROVED → PRODUCTION_DEPLOYED**. At these, `forge advance` exits 3 by design, and Forge 2.1.0 has no approve command. Only you pass them — Claude must not write `state.yaml`:

```bash
# 1. edit .forge/state.yaml by hand:  maturity.state: PLANNED  ->  SPECIFIED
forge state reset-integrity --by "Lavyd" --reason "PLANNED->SPECIFIED: constitution + ADR-001..010 approved (TASK-103)"
forge validate --strict          # must be 0
git commit -am "HUMAN GATE PLANNED->SPECIFIED approved by Lavyd: constitution + ADR-001..010 (TASK-103)"
```

Without `reset-integrity`, the next `forge sync` or `forge advance` refuses with exit 4 (tampering). `reset-integrity` prints but doesn't store `--by`/`--reason`, so the **commit message is the approval record** — write it as one.

When to pass each gate:
- **SPECIFIED:** at TASK-103.
- **IMPLEMENTED:** when every non-blocked Phase 1–5 task is `done`.
- **PRODUCTION_DEPLOYED:** after you deploy the approved artifact.

## Release sequence (Phase 6)

```bash
forge validate --strict && forge render all                  # views and AI prompt fresh, or advance refuses
# SPECIFIED -> IMPLEMENTED: human gate — see "Passing a human gate" (forge advance exits 3 here)

forge rc create --profile application
forge verify --dimension build        # ... and each required gate: typecheck lint unit integration contract e2e
                                      # security runtime self_audit accessibility performance reliability adversarial
forge repair --dimension <failed>     # on exit 7: fix code, re-run; exit 6 after 3 attempts -> escalate to a human
forge accept ACC-001 --result pass --by "<name>" --source <evidence path>   # one call per ACC-ID:
forge accept ACC-002 ...   # ... ACC-003 ACC-004 ACC-005 ACC-006 ACC-008 as each is actually exercised
forge release-check && forge advance                          # IMPLEMENTED -> VERIFIED

# deploy the SAME artifact to staging (deployment is yours, not Forge's)
forge rc create --profile staging
forge verify --dimension build --profile staging --environment staging   # also e2e, runtime
forge release-check && forge advance                          # -> STAGING_VERIFIED

forge rc create --profile production_approval
forge verify --dimension security --profile production_approval
#   + your explicit sign-off, rollback plan ADR-010 rehearsed, no exception skipping a security gate
forge release-check && forge advance                          # -> PRODUCTION_APPROVED

# deploy to production (yours), then PRODUCTION_APPROVED -> PRODUCTION_DEPLOYED: human gate (see above)
# smoke: GET /health, DB, auth, critical journey, error rate
forge rc create --profile production
forge verify --dimension runtime --profile production --environment production   # also e2e
forge release-check && forge advance                          # -> PRODUCTION_VERIFIED (needs TASK-193 handoff)
```

Status is reported Forge's way: stage and maturity from `forge status`, each gate with its evidence path, and the next action from `forge next`. "It's done", "it works" or "it's secure" are never reported without that.
