# Imara ERP — System Architecture
**Generalized construction-industry ERP, built on Materialize Vue-Laravel**
*(Formerly scoped as "REXE ERP" — renamed on generalizing away from a single roofing client, in line with the Imara product family: ImaraPay, ImaraConnect, ImaraStack.)*

**Version:** v20 · See changelog at end of document. Any PR touching a modeled entity should follow this document or update it — the source of truth should stay here, not drift silently into code.

---

## 1. Stack

- **Backend:** Laravel 12, PHP 8.2, PostgreSQL
- **Frontend:** Vue 3.5 SPA (Vuetify 3), Pinia 3, Vue Router 4 (auto-routed), Vite
- **Auth:** Laravel Sanctum (token-based) — replaces the package's mocked cookie/MSW auth
- **Authorization — two layers, not one:** CASL (frontend router-guard, already wired in the template) is a **UX layer only** — it stops a Vue route from rendering, nothing more. It does not stop an authenticated Sanctum token from hitting the API directly. **Actual authorization is enforced server-side via Laravel Policies/Gates**, one policy per entity, checked in every controller action (`$this->authorize('update', $purchaseOrder)`), backed by route-level middleware for coarse role checks. The RBAC roles in §11 map to these policies — a role listed there without a corresponding Policy class is not actually enforced, just hidden from view.
- **Multi-tenancy:** shared database, `tenant_id` (or `org_id`, matching the naming already used on Lipa Kodi and the bookkeeping app) on every tenant-scoped table, consistent with the pattern already established across your other multi-client systems rather than inventing a new one. Every query needs tenant scoping via a global model scope, not ad hoc `where()` calls — a forgotten scope on one query is a cross-client data leak. Confirm this is still the right call if Imara's actual client shape turns out to be a handful of large single firms rather than many smaller ones, in which case single-tenant-per-deployment is simpler and defensible instead. **Tenant resolution, stated explicitly since every other table's `tenant_id` references something that was never itself modeled:** a `Tenant` entity is defined in §3.1 (`name`, `status`, `plan_tier`), and every request resolves to a tenant via the authenticated `User`'s `tenant_id` — since auth is Sanctum bearer tokens (§1.1), not subdomain routing, a token is issued to a `User` who belongs to exactly one `Tenant`, and that's the tenant context for every query the request makes. No subdomain or header-based tenant switching is needed for v1; a user with access to multiple tenants (rare, but possible for an accountant serving several clients) would need explicit tenant-switching UI, which is out of scope until that need is confirmed real.
- **Background jobs:** Laravel Scheduler (cron-driven — reorder-level checks, DLP transition scans, casual-conversion threshold checks, retention-release eligibility, report caching) plus queue workers (database queue for v1, Redis as the standard upgrade path) for async work like notification dispatch. Every scheduled job wrapped in `withoutOverlapping()` — none of them are safe to run twice concurrently (a doubled reorder-level check raises a duplicate `DemandTrigger`). **Known limitation of the v1 choice:** `withoutOverlapping()` on the database queue driver is less reliable than on Redis under worker restarts — acceptable for v1 given the stated no-double-fire requirement is mostly about scheduled jobs (which use the Scheduler's own overlap lock, a separate mechanism from the queue driver) rather than queued jobs specifically, but worth remembering as a reason to prioritize the Redis upgrade once queue volume grows past trivial.
- **Routing pattern:** SPA catch-all (`routes/web.php` → single Blade shell), Laravel is a pure JSON API behind it
- **Real-time needs:** deferred to Phase 2 (see §8) — polling acceptable for v1, Laravel Echo/WebSockets is the upgrade path for the live inventory board

This document assumes the `full-version` package (javascript-version) audited previously, cherry-picking the Kanban, Invoice, and Roles/Permissions apps as UI starting points.

### 1.1 Operational Envelope

Ten rounds of review pushed exclusively on correctness — does this balance, does this reconcile, is this state machine complete. None asked what happens when the database node dies or what "fast enough" means, so none of it got specified. This section closes that gap at the level the doc otherwise operates at: targets and mechanisms, not runbooks. The actual operational runbooks (how to run a restore, who gets paged, on-call rotation) belong in an ops repo, not here — this states *what problem they solve* and *what they must guarantee*, so those runbooks have something concrete to be written against.

**Security posture.** Transport: HTTPS/TLS everywhere, HSTS enabled, CORS locked to the SPA's own origin per environment (staging and production are different origins, not a shared allowlist). Sanctum runs in **pure bearer-token mode**, not SPA cookie mode (`EnsureFrontendRequestsAreStateful`) — worth being explicit, since "token-based" in the Stack list above doesn't by itself rule out the cookie flow, and the two have different CSRF implications. Secrets live in a managed secret store in production, never a server-local `.env` alone, with rotation on staff turnover. Auth hardening: rate-limited login endpoints, a password policy favoring length over complexity rules, account lockout after repeated failures, and **all Sanctum tokens revoked immediately on password change or account termination** — not just a `status` flag flipped while old tokens keep working. **MFA is mandatory for Finance and Admin roles from Phase 1**, optional elsewhere — those two roles touch retention releases, credit approvals, and payroll, which is exactly where a compromised single-factor account does the most damage. File uploads (BOQ imports, §3.8) get a type allowlist (not a blocklist), size caps, macro-stripped `.xlsx` parsing, and the parsing library kept on a security-update cadence — this is one of the few places untrusted external input enters the system and deserves treatment as such. Inbound webhooks (M-Pesa callbacks, TalkSasa delivery receipts, KRA TIMS responses in Phase 3) require signature/HMAC verification plus replay protection (timestamp + nonce) before anything they carry is trusted. `ApprovalLimit.second_approver_role_id` (§3.10) requires a second **role** — the application layer must additionally reject the same **user** approving both stages, since one person commonly holds two roles at a small contractor, and without this check the two-approver control is decorative. `AuditLog` entries for `Payslip` changes contain salary in `old_values`/`new_values` — access to `AuditLog` itself needs its own Policy, not blanket admin-by-convention, and direct production DB access for support/ops goes through an audited bastion, never a raw connection string. Right-to-erasure (§15) resolves as: `Employee` PII fields (name, national ID, bank details) are anonymized on request; `Payslip` amounts are retained (statutory record-keeping requirement overrides erasure of the *numbers*, not the *identity*); `AuditLog` entries referencing the person have the identity reference anonymized in place rather than deleted, preserving the audit trail's integrity while satisfying the request.

**Backup & Recovery.** RPO target **15 minutes** via continuous WAL archiving (point-in-time recovery), not nightly-snapshot-only — a financial system's data-loss tolerance should be tight from day one, not backed into later. RTO target **4 hours** for a full regional outage, faster for a single-node failure. Backups stored off-site in a different availability zone/provider than primary, but still Kenya/Africa-region — a US/EU off-site location would solve backup diversity while violating the data-residency concern already raised in §15, so "off-site" and "DPA-compliant" constrain each other and both apply simultaneously. Encrypted at rest. **Restores are tested on a schedule** (monthly is a reasonable default), against a scratch environment, with results logged — an untested backup is a hypothesis, not a fact. Uploaded files (`specification_file_path`, `source_file_path`, `ComplianceDocument.file_path`) get the same treatment via S3 versioning plus cross-region replication. **The restore-vs-reversal interaction the reversal-only journal policy (§3.9) doesn't account for**: restoring a backup older than the most recent posted `JournalEntry` loses that entry with no reversal record, since the reversal policy assumes the ledger is never rewound — a restore violates that assumption structurally, not just operationally. The documented procedure: after any restore, reconcile against whatever last-known state is available (a read replica's lag point, an external notification log, a client's own records) and **re-post** anything lost as new entries dated at recovery time — never attempt to reconstruct and backdate the original entries, which would be indistinguishable from falsifying the ledger. Right-to-erasure against backups resolves practically, not instantly: an erasure request is satisfied once the pre-erasure backups have aged out of the retention window, which is stated as policy rather than promising erasure across immutable backups that can't actually support it.

**Performance targets.** Sized for the first cohort — tens of concurrent users per tenant, not thousands. p95 API response time: **under 300ms for reads, under 800ms for writes** (a `LedgerPostingService` write touches more tables than a simple read). p95 report generation: **under 2 seconds** for Trial Balance/AR-AP Aging at Phase 1 data volumes, degrading gracefully (background job plus a completion `Notification`) once a tenant crosses the ~5M-row `stock_ledger` threshold already flagged as a risk in the Two-Year Outlook — that section named the failure mode; this states the number it's measured against. Frontend initial load: **under 3 seconds** on a typical Kenyan mobile connection, which matters directly given the Site Supervisor mobile use case elsewhere in this doc. Scheduled jobs get a runtime budget scoped to their own recurrence interval (an hourly job budgeted to finish in under 10 minutes) with a `Notification` fired on overrun, not silent creep. Indexing discipline: every foreign key indexed, plus composite indexes matching the query patterns already implied by the entity model — `(tenant_id, status)` and `(tenant_id, posting_date)` on `Invoice`/`ProgressClaim`/`JournalLine`, `(item_id, warehouse_id, created_at)` on `stock_ledger`. List endpoints eager-load related models by convention (Laravel's `with()`), checked in code review rather than left to memory — the classic N+1 failure mode on an SPA that fetches invoice lists with line items. The read replica the Two-Year Outlook names as the availability-board fix is a Phase 2/3 mechanism, not Phase 1 — stated here so it isn't quietly expected to already exist. `DocumentSequence`'s row lock and `stock_ledger`'s reservation lock (§3.10, §6) serialize by design; that's an accepted tradeoff at the target user count above, and explicitly the first thing to revisit if month-end/milestone-day burst contention becomes visible in practice.

**Robustness contract.** Every inbound webhook (M-Pesa, TalkSasa, KRA TIMS in Phase 3) requires an idempotency key — duplicate delivery of the same key is a no-op, never a double-post. **Webhook-before-commit race, stated explicitly:** an unusually fast external callback (M-Pesa confirming before the initiating `Payment` row's transaction has committed) is handled by writing the `Payment` as `pending_external` and committing *before* the outbound call is made, not after — the webhook handler looks up a row that's guaranteed to already exist, rather than racing the commit that created it. Frontend financial-mutation actions (PO approval, Invoice creation, Payment recording) get disable-on-submit plus a request-level idempotency token, so a double-click can't double-post the way a retried webhook could. External dependency failure policy, stated once so every integration follows the same rule rather than each inventing its own: **the triggering business action always succeeds locally first** — raising an Invoice, approving a PO — and the external call (TalkSasa SMS, M-Pesa STK push, KRA TIMS submission) is queued and retried asynchronously, never blocking the core transaction; a failed external call after retries are exhausted raises a `Notification` rather than failing silently. **`Notification` atomicity, stated explicitly since it's genuinely ambiguous whether a notification is an internal write or an external call:** creating the `Notification` *record* is in-transaction, alongside whatever business event triggered it — the record always exists once the transaction commits. *Dispatching* it (the actual SMS/email send) is post-commit and best-effort, following the same external-dependency policy as everything else — a failed dispatch doesn't roll back the business event that raised it. Failing jobs get a dead-letter queue after N retries, surfaced via `Notification` — not left retrying forever against a poisoned message. `/health` (liveness) and `/ready` (readiness — DB and queue connectivity) endpoints are a Phase 1 baseline, not a later addition, since any real deployment setup needs them from day one. Structured logging carries a correlation ID from the initiating HTTP request through any queued job and webhook callback it spawns, so one Payment's full lifecycle is traceable end to end. Migrations on financial tables are additive-only — no column drops without a versioned deprecation window — given `AccountingPeriod` and `AuditLog` were designed for correctness under exactly this kind of schema change. **Business-time-zone, stated explicitly since it determines which `AccountingPeriod`/fiscal period a transaction lands in:** every timestamp is stored in UTC, but "the business day" — for `posting_date`, `received_at`, `paid_at`, `delivered_at`, and every other date used to bucket a transaction into a period — is always evaluated in Africa/Nairobi (EAT, UTC+3), not server-local or raw UTC; a payment at 02:00 EAT on 1 July is 1 July for every reporting and period-lock purpose, even though its UTC timestamp says 30 June. **Server-side input validation, stated as a policy rather than assumed:** every quantity field rejects zero and negative values except where a `variation_type = omission` explicitly represents a reduction (§3.7); every rate/amount field rejects negative values outright. This is the front door to ledger corruption and needs to be enforced at the API boundary, not assumed to be caught downstream by `JournalLine`'s own debit/credit validation, which only protects the posting layer, not the entities that feed it.

**What deliberately isn't here:** the full security threat model (its own document, referenced from this section once written), vendor-specific choices for backup storage/logging/monitoring providers (Phase 1 implementation decisions — this section states what problem they must solve, not which product solves it), and operational runbooks (ops repo, not architecture doc).

## 2. Source Process Model

Translated from the flowchart, with roofing-specific framing removed. Terms are defined here once and used consistently everywhere else in this document:

- **RM (Raw Materials):** inputs purchased from suppliers, not yet transformed
- **FG (Finished Goods):** items ready for sale/use — either stocked from prior production or produced on demand
- **BOM (Bill of Materials):** the recipe — which RM items and quantities produce one unit of an FG item
- **BOQ (Bill of Quantities):** the project-facing quote structure — line items with quantities/rates that make up a Quotation or Project scope
- **Soft Reserve:** a provisional hold on stock at proforma/quotation stage — doesn't remove stock from availability, just flags intent
- **Hard Reserve:** a committed hold at dispatch stage — stock is locked, unavailable to any other order
- **Reorder Level:** a stock threshold that auto-triggers a new procurement Demand Trigger

### 2.1 End-to-end flow

1. **CRM Lead → Quotation/Sales Order** → **Feasibility Check**
   - Fail → Reject/Renegotiate → (if renegotiated) back to Feasibility Check
   - Pass → **Supply Path** decision, one of four:
     - **Direct Sale** — sell from existing FG stock
     - **Manufacture for Sale** — produce FG on demand, sell immediately
     - **Manufacture for Project** — produce FG against a project's BOQ/BOM
     - **Project** — service/labour-led work against a project plan, FG may or may not be involved

2. **FG availability check** (this diamond repeats per supply path — same logic, different trigger):
   - **Available** → reserve FG (soft reserve at quotation, hard reserve at dispatch) → route to Billing
   - **Not available** → triggers **RM Manufacturing**, which does two things simultaneously:
     - Sends a **Demand Trigger** into the Procurement Process (§2.2)
     - Reserves whatever RM stock already exists for the operation

3. **Manufacture for Project** specifically inserts **Receive Plan → Generate BOQ/BOM** before the FG check, and its billing can be **milestone-based** rather than a single invoice.

4. Once FG is available (from stock or freshly produced), the flow forks by path:
   - **Direct Sale / Manufacture for Sale** → Billing Process → Delivery Process → Close Sales Order
   - **Project / Manufacture for Project** → Labour Process → Project Process → Last Milestone? (No: loop to Billing for next milestone; Yes: Project Complete)

5. **Release Labour** and **Return Surplus RM/FG** are cleanup steps that run after production/project work completes, feeding surplus back into reservable stock.

### 2.2 Procurement Process (sub-process)

```
Demand Trigger → Check Availability (C.A)
  Available     → Reserve Products/Raw Materials directly (skip purchasing)
  Not Available → Purchase Requisition → Approval → Purchase Order → Goods Delivered
                    → Quarantine Stock → QC
                        Passed → Update Inventory → Reserve Products/Raw Materials
                        Failed → Return to Supplier → Log Supplier Performance
```
Confirmed: "C.A" is *Check Availability* — an internal stock query against `stock_ledger`, not a supplier credit-limit check. This diamond queries stock, same as assumed. **Partial availability, stated explicitly since the diagram's binary shape doesn't represent it:** "Available"/"Not Available" isn't actually a binary outcome in practice — 300 of 500 required units in stock is the common case, not the edge case. The real behavior: reserve whatever quantity *is* on hand (a `SalesOrderReservation`/`RMReservation` for 300), and raise a `DemandTrigger` for exactly the shortfall (`quantity_needed = 200`), never for the full original requirement. The diagram's two branches are the two ends of a spectrum this always resolves to, not a strict either/or.

### 2.3 Billing Process (sub-process)

```
Proforma Invoice → Soft Reserve → Client type?
  Credit → Credit Approval → Received?
                                Yes → proceed to Delivery
                                No  → Cancel Order: Reverse Soft Reserve
  Cash   → Received? → same Yes/No branch
```

### 2.4 Delivery Process (sub-process)

```
Hard Reserve → Dispatch/Delivery → Update Inventory → Payment type?
  Credit → Invoice Payment: Credit → Close Sales Order
  Cash   → Receive Payment → Close Sales Order
```

### 2.5 Labour Process (sub-process)

```
Labour Demand → Labour available internally?
  Available     → Assign to Project → Block Days (calendar/capacity hold)
  Not Available → Contractors → Assign to Project → Block Days
```
Generalized note: "Labour" here is any billable resource — tradespeople, equipment operators, or subcontracted crews. Not roofing-specific in the source diagram already, kept as-is.

### 2.6 Processing FG Process (sub-process)

```
Convert to Finished Goods → QC
  Passed → Update Inventory → Reserve Products
  Failed → Evaluate → Rework/Scrap → Reserve Products (or loop back to conversion)
```

### 2.7 Project Process (sub-process)

```
Project Utilization → Quality Sign Off → Invoice Payment: Credit → Close Milestone
```

## 3. Core Entity Model

Grouped by module, with the fields that matter architecturally (not a full migration spec).

**Tenancy rule, stated once rather than repeated on every entity below:** every entity in this document carries `tenant_id`, scoped via a global Eloquent model scope (§1) — no exceptions, including reference-feeling tables like `TaxCode`, `Category`, and `StatutoryDeductionRate`, since different tenants may run different categories, rates, or chart-of-accounts setups even where the values often coincide. This is deliberately not written out 70+ times below; treat it as always present unless a specific entity explicitly says otherwise (none currently do).

### 3.1 Shared / Master Data
- **Tenant** — `name`, `status` (trial, active, suspended), `plan_tier` (nullable — a future billing/feature-tier concern, not load-bearing for v1). This is the one entity every other table's `tenant_id` implicitly references and that was never itself modeled — genuinely foundational, and `platform-foundation` cannot exit as specified without it existing first. Created once per new client during onboarding, before any of that client's other data can be seeded (the Chart of Accounts standard seed, `DocumentSequence` initialization, etc. all need a `Tenant` row to attach to).
- **UserInvitation** — `tenant_id`, `email`, `role_id`, `invited_by`, `token`, `expires_at`, `accepted_at` (nullable). The mechanism behind §9's first-run onboarding checklist item "invite users" — an admin creates an invitation, the invitee follows a tokenized link to set a password and activate their `User` row, rather than an admin creating accounts and distributing passwords directly.
- **Party** — unified customer/supplier/contractor. `type` (customer, supplier, contractor, both), `credit_limit`, `payment_terms`, `tax_residency_status` (resident_certified, resident_uncertified, non_resident — determines default `TaxCode` for WHT, §3.9), `is_active`
- **User** — Laravel's default model, extended: `employee_id` (nullable — an admin login with no payroll record has no Employee; a casual labourer who never logs in has no User), `role_id`. **User ↔ Employee is optional 1:1 in both directions**, not required either way. `ResourceAssignment` (§3.6) assigns a `Resource`, which links to `Employee` when internal — not directly to `User` — since who's scheduled on a project and who can log in are genuinely separate questions.
- **Item** — `sku`, `name`, `category_id`, `type` (raw_material, finished_good), `uom_id`, `reorder_level`, `is_active`, `standard_cost` (nullable — only meaningful when `Category.valuation_method = standard_cost`; the enum offered the option without this field existing to back it, a gap same-shaped as the ones closed elsewhere in this document). **Standard cost variance, resolved rather than left implicit:** when actual GRN unit cost differs from `standard_cost`, the difference posts to a **Purchase Price Variance** account (added to §3.1's seed) rather than silently adjusting `standard_cost` itself or being absorbed into Inventory at the wrong value — `standard_cost` only changes via an explicit revision (a cost-update action, logged like any other rate change), never as a side effect of a single purchase.
- **Category** — hierarchical, industry-agnostic (no roofing-specific taxonomy), `valuation_method` (fifo, weighted_average, standard_cost) — set per category rather than system-wide, so e.g. imported materials can run FIFO while locally sourced ones run weighted average, in the same system (borrowed from Odoo's Stock Valuation Layers)
- **UnitOfMeasure** — `code`, `name`, conversion factors where needed (e.g., bags↔kg)
- **BillOfMaterials (BOM)** — `finished_good_item_id`, line items of `raw_material_item_id` + `quantity`, `wastage_allowance_pct`, `tolerance_pct` (nullable — defaults to `wastage_allowance_pct` if not separately set; lets a project-specific BOM tighten the tolerance without changing the standard allowance), `source` (uploaded, generated, manual), `project_id` (nullable — a BOM can be product-standard or project-specific)
- **ChartOfAccounts** — `code`, `name`, `account_type` (asset, liability, equity, revenue, expense — what the Balance Sheet and Income Statement group by, §10.1), `sub_type` (nullable — the finer classification a Balance Sheet actually needs to present separately, not just fold into the top-level type: `cash`, `bank`, `receivable`, `retention_receivable`, `inventory`, `fixed_asset`, `payable`, `retention_payable`, `statutory_payable`, `equity_reserve`. Without this, "Retention Receivable" and "Statutory Payables" would have nowhere to be their own labeled Balance Sheet line, which an auditor expects), `parent_account_id` (nullable, self-referencing — lets individual statutory payables (PAYE Payable, NSSF Payable, VAT Payable, etc.) each be their own account for posting/reconciliation purposes while still rolling up to a single "Statutory Payables" line for presentation), `is_contra` (boolean — true for Accumulated Depreciation and similar accounts that reduce their parent type's balance rather than adding to it), seeded per tenant.

  **Standard seed** — the default Chart of Accounts every new tenant starts with, so the first client can post a journal entry on day one rather than discovering there's no default to fall back to. Each account is listed under exactly one `account_type` section, matching what it actually is — `sub_type`/`parent_account_id`/`is_contra` (§3.1 above) carry the finer classification, rather than an account being cross-listed with a flag explaining why the section it's sitting in is wrong for it:
  - *Assets:* Cash/Bank *(one account by default — every §7 posting references it as a single name; split into `Cash` and `Bank` as `sub_type`-differentiated children only if a tenant specifically needs cash-on-hand vs. bank-balance reporting, still rolling up to one Balance Sheet line)*, Accounts Receivable, Retention Receivable, VAT Input/Receivable, WHT Receivable/Tax Credit, Inventory (RM), Inventory (FG), Fixed Assets at Cost, Accumulated Depreciation *(contra, `parent_account_id` → Fixed Assets at Cost)*
  - *Liabilities:* Accounts Payable, Retention Payable, VAT Payable, PAYE Payable, NSSF Payable, SHIF Payable, Housing Levy Payable, HELB Payable, NITA Payable, WHT Payable, Other Deductions Payable, Net Pay Payable, Customer Advance, **Landed Cost Payable** *(one consolidated account for freight/duty/clearing/insurance, not one per cost type — `postLandedCostAllocation`'s `cost_type` parameter distinguishes the source `LandedCost` record it came from, not a field carried on the `JournalLine` itself; `JournalLine` has no memo field, so the per-cost-type breakdown is reachable via the posting's `reference_id`, not stored redundantly on the line. Not a reason to seed four near-identical payable accounts a tenant would have to reconcile separately)*, **Loan Payable** *(for `CapitalMovement`, below)*

  **A deliberate consolidation worth flagging, not an oversight:** `Accounts Receivable` is also where a post-acceptance supplier return posts when Imara had already paid for the returned goods (§7 — the supplier now owes a refund, and there's no separate "amounts owed back by suppliers" account). This mixes customer receivables with supplier refunds-due in one control account and one AR Aging report line. Fine for most small contractors; a tenant whose auditors want the two split apart would add a second receivable account and route that specific posting to it — a configuration choice, not a schema change.
  - *Equity:* Retained Earnings, Retained Earnings (Opening) *(a distinct account, not a tag on the same one: `postOpeningBalance`'s plug figure needs to be traceable back to the migration event specifically, separable from ordinary period-close retained earnings, so a client's true post-migration trading result isn't blended with whatever equity position they walked in with — reports treat the two as one Balance Sheet line for presentation, but they're separate ledger accounts)*, Asset Revaluation Reserve, **Owner Capital** *(for `CapitalMovement`, below)*, **Drawings** *(contra-equity — `capital_withdrawn` debits this, not Owner Capital directly, so capital contributed and capital withdrawn stay separately visible for audit rather than netting against each other inside one account balance)*
  - *Revenue:* Revenue, Gain on Disposal, FX Gain
  - *Expenses:* COGS, Salary/Wages Expense, Employer Statutory Expense, NITA Expense, Depreciation Expense, Subcontract Expense, Scrap/Variance Expense, Wastage Variance Expense, Wastage Variance *(a favorable-variance counterpart account, not a true contra-expense — a peer P&L line sitting alongside Wastage Variance Expense, credited when less RM is consumed than the BOM standard implies, so a reader sees both directions distinctly rather than one account that sometimes nets negative. Doesn't carry `is_contra`/`parent_account_id` the way Internal Equipment Recovery below does — the two entries look similar in the posting logic (both get credited to offset a cost) but aren't the same structural relationship, and calling this one "contra" too would be describing it by resemblance rather than by what it actually is)*, Bad Debt Expense, FX Loss, Loss on Disposal, P&L Impairment Expense, **Purchase Price Variance** *(only populated for items under `valuation_method = standard_cost` — the difference between `Item.standard_cost` and actual GRN unit cost)*, Project Equipment Cost, Internal Equipment Recovery *(a true contra-expense, `is_contra = true`, `parent_account_id` → Project Equipment Cost — nets against it the same way Accumulated Depreciation nets against Fixed Assets at Cost above)*
  - This is a generic construction-sector seed, not roofing- or trade-specific, matching the rest of this document's generalization — a tenant remaps or extends it, doesn't replace it wholesale.

### 3.2 CRM & Sales
- **Lead** — `party_id` (nullable if prospect), `source`, `status`
- **FeasibilityAssessment** — `sales_order_id`, `assessed_by`, `assessed_at`, `result` (pass, fail, conditional), `notes`, `conditions` (nullable — populated when `result = conditional`). Without this, the `feasibility_check → renegotiating → feasibility_check` loop in the state machine (§5.1) has no record of what was actually renegotiated between passes — only the latest status persists, and the history is lost. A SalesOrder can go through several of these before it's approved; each pass gets its own row. **`SalesOrder.feasibility_status` transition rule, stated explicitly:** it always mirrors the *most recent* `FeasibilityAssessment.result` for that SalesOrder — `pass` advances the state machine, `fail` triggers Reject/Renegotiate, `conditional` holds the SalesOrder in place until a further action resolves it: either a new `FeasibilityAssessment` recording that the stated `conditions` were met (a fresh row, `result = pass`), or an explicit manual override by the assessor. `conditional` is never auto-promoted to `pass` by any passage of time or unrelated event.
- **Quotation / SalesOrder** — `lead_id`, `party_id`, `project_id` (nullable — see §3.7 note), `supply_path` (enum: direct_sale, manufacture_for_sale, manufacture_for_project, project), `feasibility_status`, `invoice_policy` (on_order, on_delivery, on_milestone), `status` (state machine, §5.1)
- **SalesOrderLine** — `sales_order_id`, `item_id` (nullable — a line can be a described service with no stock item, same as `BOQLine`), `description`, `quantity`, `rate`, `amount`. **This was missing entirely** — Direct Sale and Manufacture-for-Sale, the two simplest and most common supply paths, had no way to say "5 units of SKU-123 at KES 4,500" without it; the BOQ structure only scopes to Project/Subcontract (`boqable_type`), not SalesOrder, and shouldn't be stretched to cover a use case it wasn't designed for — a Direct Sale doesn't need sections, measurement sheets, or markups, it needs a flat line-item list, which is exactly what `BOQLine` would be if all the project-specific structure were stripped off. `SalesOrderReservation` (below) reserves stock against these lines.
- **Delivery** — `sales_order_id`, `delivered_at`, `status` (pending, dispatched, delivered). The event that actually marks goods as shipped — previously implied by the flowchart's "Delivery Process" (§2.4) and referenced by the COGS-recognition ledger row (§7), but never modeled as a record a user or system creates. This is what an `invoice_policy = on_delivery` SalesOrder is actually waiting on (see the trigger rule below), and what the `Delivery (COGS recognition)` ledger posting (§7) references as `reference_id`.
- **DeliveryLine** — `delivery_id`, `sales_order_line_id`, `quantity_delivered`, `cogs_value` (the portion of that line's COGS this specific delivery recognizes). Mirrors `GRNLine`'s relationship to `PurchaseOrderLine` (§3.4) — without it, delivering 300 of a 500-unit `SalesOrderLine` has no representation, no partial COGS recognition, and no way for a second, later delivery of the remaining 200 to know what's already been shipped. `Delivery.status` reaching `delivered` (used by the `on_delivery` trigger rule below) means every line's cumulative `DeliveryLine.quantity_delivered` meets or exceeds its `SalesOrderLine.quantity` — a partial delivery leaves the `SalesOrder` in a `partially_delivered` state (added alongside the existing states in §5.1) rather than forcing an artificial second order for the remainder, the same resolution already used for `PurchaseOrder`'s partial-receipt case (§5.2).
- **SalesReturn** — `delivery_id`, `sales_order_line_id`, `quantity_returned`, `reason` (over_ordered, wrong_spec, damaged), `restock_status` (pending_qc, restocked, scrapped), `credit_note_id` (nullable, links the returned-goods side to the revenue-reversal side once the corresponding `CreditNote` is raised). **Promoted to Phase 1 rather than left as manual-Credit-Note-plus-hope**, since Credit Notes alone reverse revenue but do nothing to inventory — a return that's only a Credit Note leaves stock permanently understated by whatever was actually returned. A returned item goes through the same `QualityCheck`/`StockQuarantine` path as an incoming GRN before it's restocked (damaged goods get scrapped, not silently added back to available stock).
- **BOQ** — `boqable_type`/`boqable_id` (polymorphic — a BOQ scopes to a Project *or* a Subcontract, since §3.4's `Subcontract.schedule_of_values` explicitly reuses this table; a single `project_id` FK couldn't support both), `revised_contract_value` (nullable until the first Variation Order is approved — see §3.7), `uses_sections` (boolean), `source` (uploaded, generated, manual), `source_file_path` (nullable — the uploaded spec document, when applicable)
- **BOQSection** — `boq_id`, `parent_section_id` (nullable, self-referencing — supports sub-sections like "Substructure > Excavation > Bulk Excavation"), `name`, `sequence`. Rolls up quantities/values from its lines and child sections. **Optional** — a BOQ with no sections just has lines attached directly (`section_id` null), which is the simple-client case.
- **BOQLine** — `boq_id`, `section_id` (nullable), `description`, `quantity`, `rate`, `amount`, `item_id` (nullable — BOQ lines don't always map 1:1 to a stock item), `line_type` (standard, provisional_sum, prime_cost_sum, preliminaries)
- **MeasurementSheet** — `boq_line_id`, `period`, `previous_qty`, `current_qty`, `cumulative_qty`, `certified_qty` (nullable — distinct from `current_qty`: what's claimed is submitted to the client's QS/consultant for certification *outside* the system, and it's `certified_qty` that drives billing once it comes back, not the submitted figure. `status` tracks the internal workflow (draft, submitted, approved) up to the point of external submission; certification itself is recorded by entering `certified_qty` when the response arrives), `status` (draft, submitted, approved). This is what an Interim Payment Certificate is generated from — field-measured quantities against a BOQ line, tracked period over period. **Only populated when a project needs certified IPCs**; clients who don't need certification just bill off `BOQLine.quantity` directly and never touch this table. **Invoice trigger, stated explicitly:** `MeasurementSheet.status` reaching `approved` (i.e. `certified_qty` has been entered) is what triggers IPC/Invoice generation for that line — not a separate manual "Generate IPC" action and not a scheduled batch run, though a scheduled job may *notify* the biller that certified lines are ready to invoice (reusing `Notification`, §3.10) rather than generate the Invoice unattended.
- **Markup** — `section_id` (nullable) or `boq_id`, `type` (overhead, profit, contingency, statutory_levy), `percentage`. **Deliberately no `tax` type** — VAT is handled entirely by `TaxCode`/`Invoice.vat_amount` (§3.9), computed at invoicing time from `gross_amount`, not baked into the BOQ's contract value. `statutory_levy` covers something genuinely different: project-level statutory charges that *are* part of the contract price itself (e.g., NCA training levy, county cess) — these get added to `revised_contract_value` like any other markup, whereas VAT sits outside it entirely. Two mechanisms, deliberately not merged, since conflating them would mean VAT could disagree with itself depending on which one was consulted.

Since section-based IPC certification is only needed for *some* clients (confirmed), the schema supports both without a mode switch: `uses_sections = false` means lines attach straight to the BOQ and billing reads `BOQLine.quantity` directly — same tables, no sections/measurement sheets populated, no extra complexity surfaced to that client's screens. `uses_sections = true` is the full QS-grade structure. One schema, two depths of use.
- **SalesOrderReservation** — `sales_order_id`, `item_id`, `reserve_type` (soft, hard — the current commitment *level*, mutable: escalates soft→hard at dispatch, not a lifecycle stage), `quantity`, `status` (active, consumed, released — the *lifecycle*, orthogonal to `reserve_type`, matching §5.3). These are two different questions and were previously conflated into one field: "how committed is this reservation" (`reserve_type`) versus "is this reservation still live" (`status`).

`invoice_policy` replaces what was implicit branching logic in §2.3/§2.7 (Direct Sale bills once, Project bills per milestone) with a data field — a future supply path or client-specific billing arrangement becomes a config change, not a code change (borrowed from Odoo's Sales Order invoicing policy). **The transition trigger for each value, stated explicitly since none of the three were previously specified:** `on_order` — the Invoice is raised automatically the moment the SalesOrder reaches `approved` (§5.1), since the whole order is billed upfront, nothing to wait on. `on_delivery` — triggered by the `Delivery` record above reaching `status = delivered`; a scheduled reconciliation checks for delivered-but-not-yet-invoiced orders as a safety net, but the primary trigger is the delivery event itself, not a batch job. `on_milestone` — already covered by `Milestone.status` reaching `signed_off`/`invoiced` (§3.7) or, for measurement-driven billing, `MeasurementSheet.status = approved` above.

### 3.3 Inventory & Stock
- **StockLedger** — append-only *physical movement* log only: `item_id`, `warehouse_id`, `location_id` (nullable — bin/sub-location, cheap to add now, full WMS location hierarchy stays a Phase 2/backlog build), `movement_type` (receipt, issue, transfer_out, transfer_in, production_consumption, production_output, adjustment, scrap, return), `quantity`, `unit_cost`, `reference_type`, `reference_id`. **A transfer between warehouses is two rows, not one** — `transfer_out` at the source `warehouse_id`, `transfer_in` at the destination, sharing a `reference_id` linking them. **In-transit stock** (goods that have left the source but not yet arrived) is represented by a designated "In Transit" `Warehouse` record — `transfer_out` lands the goods there, not nowhere, so they remain visible in the availability computation and the Procurement dashboard's goods-in-transit widget (§10) the whole time, and `transfer_in` moves them from "In Transit" to the real destination. **Reservations are never a `movement_type` here** — they live entirely in `SalesOrderReservation` (§3.2) as commercial commitment, not physical fact. Available quantity is `stock_ledger` on-hand minus active hard reservations, computed at read time, not stored. This is the single source of truth the "availability board" reads from (see §6). On-hand value is always computed by summing this log per the item's category `valuation_method`, never stored as a running balance (Odoo's Stock Valuation Layer pattern).
- **StockQuarantine** — `grn_id`, `item_id`, `quantity`, `qc_status` (pending, passed, failed)
- **SupplierPerformanceLog** — `party_id` (supplier), `po_id`, `event_type` (on_time, late, qc_failed, returned), `notes`

### 3.4 Procurement
- **DemandTrigger** — `source_type` (manual, reorder_level, manufacturing), `source_id`, `item_id`, `quantity_needed`, `status`. **Reorder-level deduplication, stated explicitly** — the scheduled job comparing on-hand against `items.reorder_level` (§6) only raises a new `DemandTrigger` if no `DemandTrigger` with `status` still open already exists for that item/warehouse; without this rule, an item sitting below reorder level for a week under a daily job produces seven duplicate triggers, not one.
- **PurchaseRequisition** — `demand_trigger_id`, `status` (draft, pending_approval, approved, rejected)
- **PurchaseRequisitionLine** — `requisition_id`, `item_id`, `quantity_needed`, `notes`. Same gap as `SalesOrder`/`Invoice` (§3.2/§3.9) had — a PR with no lines can't actually specify what's being requisitioned beyond the single `DemandTrigger` item it originated from, and a PR can reasonably bundle several items into one requisition even when only one triggered it automatically.
- **PurchaseOrder** — `requisition_id`, `party_id` (supplier), `currency_id`, `exchange_rate` (rate to base currency at PO date), `status` (state machine, §5.2). **Cardinality, stated explicitly:** `requisition_id` is a plain FK on `PurchaseOrder`, which already means many POs can reference one PR — nothing further is needed to support splitting a single requisition across multiple suppliers; a `PurchaseRequisition` is fully satisfied once its lines' requested quantities are covered across all POs referencing it, not necessarily by exactly one.
- **PurchaseOrderLine** — `purchase_order_id`, `requisition_line_id` (nullable), `item_id`, `quantity_ordered`, `unit_cost`. Same class of gap as `PurchaseRequisitionLine` — without this, a PO has no way to state what was ordered at what price per item, and partial-delivery tracking (below) has nothing to compare `GRNLine.quantity_received` against.
- **GoodsReceiptNote (GRN)** — `po_id`, `quarantine_status`. `stock_ledger.unit_cost` is always recorded in base currency (quantity × rate × `exchange_rate`) — the ledger never carries mixed-currency ambiguity, only the source PO/Invoice does. **Which unit cost, resolved per `Category.valuation_method` (§3.1):** `fifo`/`weighted_average` categories record the actual GRN cost; `standard_cost` categories record `Item.standard_cost` instead, with the actual-vs-standard difference posting to Purchase Price Variance (§7) rather than affecting the value carried in `stock_ledger` at all.
- **GRNLine** — `grn_id`, `po_line_id` (references `PurchaseOrderLine`), `item_id`, `quantity_received`, `unit_cost`, `quarantine_status`. Named explicitly here since `LandedCost` allocates proportionally across these rows — "line items received" was previously left unmodeled prose, referenced by another entity that needed it to actually be a table. **Partial delivery is a many-GRNLine-to-one-PurchaseOrderLine relationship** — a `PurchaseOrderLine.quantity_ordered` of 1,000 delivered across two shipments is two `GRNLine` rows against the same `po_line_id`, each with its own `quantity_received`. `PurchaseOrder.status` (§5.2) reaching `received` means every line's cumulative `GRNLine.quantity_received` meets or exceeds its `quantity_ordered` — a partial delivery leaves the PO in a `partially_received` state (added to §5.2) rather than forcing an artificial second PO for the remainder.
- **LandedCost** — `grn_id`, `cost_type` (freight, duty, clearing, insurance), `amount`, `currency_id`, allocated across the GRN's `GRNLine` rows proportionally to value or weight, converted to base currency at posting — raised as a gap in §13, formalized here now that it's part of the valuation flow (§7). This is the direct reason `currency_id` moved to Phase 1 on PO/GRN rather than staying fully in backlog (§14) — freight/duty/clearing on imports is routinely foreign-currency, and LandedCost was already Phase 1. Full multi-currency reporting (revaluation, FX gain/loss on rate movement between GRN and payment) stays backlog; this is the minimum needed for landed cost to mean anything.
- **QualityCheck vs. `StockQuarantine.qc_status`, authority stated explicitly:** `QualityCheck` (§3.5) is the authoritative record — one row per inspection, with `evaluator_id` and `disposition`, for both `GRNLine` and `ProductionOrder`. `StockQuarantine.qc_status` (§3.3) is a denormalized summary field kept in sync by whatever `QualityCheck` was most recently recorded for that stock — convenient for a fast status-only query, never the source of truth if the two ever disagree.
- **RMReservation** — `production_order_id`, `item_id`, `quantity`, `status` (active, consumed, released) — mirrors `SalesOrderReservation`'s shape but reserves raw material stock against a `ProductionOrder` rather than finished-goods stock against a `SalesOrder`. §2.2's flowchart already describes procurement reserving RM after QC pass; there was no entity for it to reserve *into*, only the FG-side reservation existed.
- **Three-way match (PO/GRN/supplier invoice), scope stated explicitly:** full automated matching is backlog (§14). Without it, Phase 1's control is manual — the AP clerk confirms the supplier's invoiced amount against the GRN's received quantities and `LandedCost` before a `ProgressClaim`-equivalent bill is certified for a straight supplier purchase (as opposed to a `Subcontract`, which already has `ProgressClaim` certification as its control point). This is an accepted manual control for Phase 1, not an oversight — the same category of tradeoff already made elsewhere in this document (e.g. `ComplianceDocument` blocking at certification rather than automated continuous monitoring).
- **Supplier payment — the AP-side equivalent of "Payment received from client," previously missing outright.** Modeled as `Payment` with `direction = disbursement` (§3.9 already has this field), `reference_type`/`reference_id` pointing at the `PurchaseOrder` or `Subcontract`/`ProgressClaim` being paid (§3.9 already has these fields too — this was a missing *event*, not a missing *field*). See §7 for the posting.
- **Subcontract** — `party_id` (subcontractor), `project_id`, `schedule_of_values` (its own mini-BOQ — a `BOQ` record with `boqable_type = Subcontract` per §3.2's polymorphic scoping, not a separate structure), `required_document_types` (JSON array, e.g. `["insurance", "tax_compliance"]` — defaults to a standard set but configurable per subcontract, since the required `ComplianceDocument` set for a KES 50,000 supply-only subcontract shouldn't necessarily match a KES 5M structural package; §3.10's certification-blocking check reads this list, not a hardcoded global one), `status`. **No `retention_terms_id` FK** — `ContractRetentionTerms.contract_type`/`contract_id` already points *at* the Subcontract (§3.9); having the Subcontract also point back at its terms is redundant and can drift (a stale `retention_terms_id` pointing at the wrong row). Query direction is always `ContractRetentionTerms` filtered by `contract_type = Subcontract, contract_id = X`, never the reverse. Distinct from `PurchaseOrder` because subcontractor spend is progress-claimed and retention-bearing, not a single delivery — the Labour Process (§2.5) only ever covered resource assignment and day-blocking, not award, scope, or claims.
- **ProgressClaim** — `subcontract_id`, `period`, `amount_claimed`, `amount_certified` (gross — WHT and VAT are both computed from this figure, per §7), `vat_amount` (computed, mirrors `Invoice.vat_amount`), `retention_amount` (computed on `amount_certified`, pre-VAT), `wht_tax_code_id` (references the payee-appropriate `TaxCode`, §3.9, resolved from the subcontractor's `Party.tax_residency_status`), `wht_amount` (computed and **stored**, not recalculated later — same immutability principle as valuation layers elsewhere in this doc: if WHT rates change after certification, the historical entry shouldn't silently drift), `net_payable` (`amount_certified + vat_amount − retention_amount − vat_on_retention − wht_amount`), `subcontractor_invoice_number` (nullable — the subcontractor's own tax invoice/ETR reference, since without it the audit trail from claim → payment has no tax-document anchor at the subcontractor end), `subcontractor_invoice_date` (nullable), `status` (submitted, certified, disputed, **reversed** — added: real construction subcontracts routinely certify work in one month and dispute it after a failed inspection the next. `certified → reversed` posts a mirror-image reversing `JournalEntry` (§3.9's `reverse()` method, same mechanism used everywhere else — this was never a missing *mechanism*, just a missing *trigger* for this specific entity) referencing the original claim, and the claim can be re-certified as a fresh row once resolved rather than editing the disputed one in place) — the subcontractor-side equivalent of a Milestone billing cycle. WHT is calculated and posted here, at certification (§7) — not deferred to payment, and not revisited at payment time.

### 3.5 Manufacturing
- **ProductionOrder** — `bom_id`, `sales_order_id` (nullable — can be for stock), `warehouse_id` (where the FG output lands — not assumed, stated explicitly since it wasn't before), `quantity`, `status`
- **QualityCheck** — polymorphic, used by both GRN (incoming RM) and ProductionOrder (outgoing FG): `checkable_type`, `checkable_id`, `result` (pass, fail), `evaluator_id`, `disposition` (accept, rework, scrap)

### 3.6 Labour & Resourcing
- **Resource** — `type` (internal, contractor), `party_id` (nullable for internal staff), `employee_id` (nullable — set when `type = internal` and the person is a payroll employee, §3.11), `skill_category`
- **ResourceAssignment** — `resource_id`, `project_id` or `sales_order_id`, `block_start_date`, `block_end_date`, `status` (scheduled, active, completed, cancelled). **Transition rule, stated explicitly:** `scheduled → active` fires automatically when `block_start_date` is reached (a scheduled job, same category as the reorder-level/DLP scans), not a manual "mark on-site" click that site staff would routinely forget; `active → completed` fires the same way against `block_end_date`. Either transition accepts a manual override (an assignment ending early, or extended past its planned date) — the automatic date-driven default handles the common case, the override handles the exception, neither is assumed to be the only path.

`Resource` stays the project-facing record (who's assigned where, for how long); `Employee` (§3.11) is the HR-facing record (contract, pay, statutory deductions). They link via `resource_id`/`employee_id` rather than merging, since a Resource can be a contractor with no HR record at all, and Timesheet data needs to flow from project assignment into payroll without the two modules owning each other's data.

### 3.7 Projects
- **Project** — `party_id`, `name`, `specification_file_path` (nullable — the uploaded project spec document), `status`. **A Project is created before its BOQ/BOM, not after** — see §3.8 below for how the two get populated.
- **Milestone** — `project_id`, `sequence`, `description`, `billing_amount` (derived, not entered freestanding), `boq_line_allocations` (many-to-many, `BOQLine` ↔ `Milestone` with a `percentage_of_value` per line — **the single primitive**, chosen over the earlier two-path design because a value-based split is what milestone billing means in practice; a section-level allocation is a shorthand that expands to 100%-of-value on every line in that section at allocation time, not a second billing mechanism. Quantity-based progress lives entirely in `MeasurementSheet`/IPC — that's a different, separate billing method, not something the Milestone entity also tries to represent), `billing_locked` (boolean, set `true` once `status` reaches `invoiced`), `status` (pending, utilized, signed_off, **rework_required**, invoiced, closed — `rework_required` added: a client can reject a milestone after sign-off but before invoicing, which happens via raising a `Defect` (§3.7) against the milestone and moving it `signed_off → rework_required`, freezing billing without needing a separate rejection concept; once the rework is verified the milestone returns to `utilized` and proceeds normally. If a milestone was already `invoiced` when the client disputes it, that's handled by a `CreditNote` against the resulting Invoice, not a Milestone state change — the milestone itself doesn't reopen once billing is a legal fact). Locking matters for Variation Orders (below): once a milestone is invoiced, its billing is a transacted, legal fact and a later VO can't retroactively change it — VO-driven recalculation only touches milestones with `billing_locked = false`. **UI pattern, not a schema concern but worth stating so it isn't discovered mid-build:** allocating every `BOQLine` to every `Milestone` individually doesn't scale past a small BOQ (a 200-line BOQ with 8 milestones is 1,600 potential allocations, nearly all zero). The intended interaction is bulk assignment at the `BOQSection` level (allocate a whole section to a milestone in one action, defaulting every line under it to 100%), with per-line override available for the exceptions — not a 1,600-cell grid presented by default. **Concurrency, stated explicitly:** two approvers signing off the same Milestone simultaneously is prevented by the state check running inside a transaction with a row lock on the `Milestone` — the state machine already forbids `signed_off → signed_off`, but only if that check and the write are atomic; checked-then-written as two separate statements is exactly the gap a race slips through.
- **VariationOrder** — header entity: `project_id`, `variation_number`, `description`, `status` (draft, submitted, approved, rejected, executed), `approved_by`, `second_approved_by` (nullable), `submitted_date`, `approved_date`, `executed_date` (nullable). **No stored `approval_chain_id`** — `ApprovalLimit` (§3.10) is a configuration rule, not a per-transaction reference; who's required to approve is looked up at submission time by querying `ApprovalLimit` for `entity_type = variation_order` against the VO's total `amount_delta`, not stored as a foreign key on the VO itself. `approved_by`/`second_approved_by` record who actually approved, for audit purposes — a separate concern from which rule determined they needed to. **`approved → executed` transition trigger, stated explicitly:** `approved` is the commercial decision (the BOQ is already recalculated at this point, per below); `executed` is a separate, manual confirmation — typically by the Project Manager — that the varied work has actually been carried out on site. The two are deliberately not the same event: a VO can be commercially approved well before the additional work is physically executed, and only someone on site can attest to the latter.
- **VariationOrderLine** — `variation_order_id`, `boq_line_id` (nullable — null for a wholly new item), `section_id` (nullable — for a variation introducing a new section), `variation_type` (quantity_change, rate_change, new_item, omission), `quantity_delta`, `rate_delta`, `amount_delta`, `description`. A single variation commonly touches several BOQ lines at once (a design change altering quantities across multiple items) — one `VariationOrder` grouping many `VariationOrderLine` rows is the real commercial unit, not one VO per line. On approval, each line mutates its `BOQLine`/`BOQSection`, and `BOQ.revised_contract_value` (**post-markup** — the sum of BOQ lines *plus* all applicable `Markup` entries, since the contract value a client sees is always post-markup; the pre-markup subtotal is available as a separate computed field for internal margin views) is recalculated as the sum — every downstream completion-percentage and billing calculation references the revised value, not the original. **Milestone recalculation on approval**: any `Milestone` with `billing_locked = false` (§3.7) has its `billing_amount` recalculated against the revised BOQ; locked (already-invoiced) milestones are untouched — a VO affects future billing, not a legal document already issued. **Concurrency, stated explicitly:** two VOs submitted against overlapping `BOQLine`/`BOQSection` rows, approved simultaneously, is prevented the same way as Milestone sign-off above — the BOQ mutation on approval runs inside a transaction holding a row lock on the affected `BOQLine`/`BOQSection` rows, and a second VO approval touching an already-locked line queues or fails with an explicit retry message, never a silent lost update. **`VariationOrderReversal`** — a compensating record referencing the original `VariationOrder`, with its own line rows carrying the *negative* of the original deltas: for when a VO is approved, work begins, and the client then cancels it. This re-reverts `BOQ.revised_contract_value` and any not-yet-`billing_locked` Milestones exactly as the original approval mutated them forward — not a manual correction, since "approved then retroactively cancelled" is a normal enough construction scenario to deserve its own modeled path rather than an ad hoc journal fix.
- **Project completion percentage** — canonical definition, gated on `invoice_policy` (§3.2) rather than on `uses_sections`, which was the ambiguous version of this rule: a Milestone always links to specific BOQ lines via `boq_line_allocations` regardless of whether the BOQ uses sections, so "uses_sections" isn't actually what determines which calculation applies. **If `invoice_policy = on_milestone`:** completion = sum of `Milestone.billing_amount` where `status ∈ {signed_off, invoiced, closed}` ÷ `BOQ.revised_contract_value`. **Otherwise (measurement-driven billing):** completion = sum of `BOQLine.amount` for lines with a certified `MeasurementSheet` ÷ `BOQ.revised_contract_value`. A project picks one billing mechanism via `invoice_policy` and stays on it — these are alternatives, not two calculations that can both apply to the same project simultaneously. Milestone-count-based ("3 of 5 milestones closed") and quantity-based (`certified_qty` ÷ `BOQLine.quantity`) remain valid *derived views* for dashboards regardless of which mechanism is canonical. Cost-based percentage-of-completion stays out of scope entirely, since that's the WIP method already deferred (§8).
- **Defect** — `project_id`, `subcontract_id` (nullable — set when the defect is attributable to a specific subcontractor's work, so subcontract retention release can filter to "defects attributable to this subcontract" without manual cross-referencing), `milestone_id` (nullable), `description`, `severity` (minor, major, critical), `blocks_retention` (boolean, set at review — not every open defect should hold back a multi-million-shilling release; a hairline crack in a non-structural wall shouldn't block it, so this is an explicit call at triage, not an automatic consequence of `status`), `reported_by`, `reported_date`, `target_fix_date`, `status` (open, in_progress, rectified, verified, closed). Feeds the retention-release gate in §3.9 — the second-stage retention release cannot reach `ready` while a Defect with `blocks_retention = true` on that project (or that specific subcontract) is still `open` or `in_progress`.
- **AnalyticAccount** — `project_id` (nullable — can also represent a cost center or overhead pool, not just a project), `name`, `type` (project, cost_center, overhead), `cost_code` (nullable — a light tag like `02-100` for "Earthworks", not a full WBS hierarchy; lets construction users filter/report by trade category now without building the full Project→Phase→Section→Activity structure a review suggested — that stays backlog). Every `JournalLine` optionally tags one of these, independent of the Chart of Accounts (§3.9). This replaces scattering `project_id` across every transactional table as the way to get per-project P&L — instead, one journal-level tag on every line gives you revenue minus every cost that touched that project (materials, labour, overhead) without redesigning the ledger (borrowed from Odoo's Analytic Accounting).

**Note on `sales_orders.project_id`:** a SalesOrder always references a Project when `supply_path` is `project` or `manufacture_for_project`. Whether Direct Sale / Manufacture for Sale orders should *also* optionally attach to a Project (purely for per-project record-keeping, without triggering the Project/Milestone workflow) is an open question — see §12.5. With AnalyticAccount now handling per-project financial rollups independently of `sales_orders.project_id`, this becomes lower-stakes either way — the reporting doesn't depend on getting this FK right everywhere.

### 3.8 BOQ/BOM Sourcing
Per the requirement that BOQ/BOM are recorded per project and can be uploaded or generated:
- **Upload path:** the project specification document (Excel/PDF/Word) is uploaded against the Project, stored at `specification_file_path`, and parsed into BOQ/BOM line items — same document-parsing pattern already used in the bookkeeping app's statement import (Excel/CSV/PDF → staged rows → confirm/edit → post). Parsed rows land in **`BOQImportStaging`** — `project_id`, `source_file_path`, `raw_row_data` (JSON, the parsed-but-unmapped row), `mapped_item_id`/`mapped_section`/`mapped_quantity`/`mapped_rate` (nullable until a reviewer confirms the mapping), `status` (pending_review, confirmed, rejected), `reviewed_by`. This was previously described only as "a staging table," referenced but never modeled — a `BOQLine`/`BOQSection` is only created from a `BOQImportStaging` row once it reaches `confirmed`, since automated extraction from varied spec formats needs human confirmation, not blind trust.
- **Generated path:** BOQ/BOM built directly in the system from the Project's requirements — standard line-item entry against existing Items/Categories, or assembled from existing BOM templates for known FG items.
- Either path produces the same BOQ/BOM records downstream — the `source` field is for audit/traceability only, not a different schema.

### 3.9 Finance
- **ProformaInvoice** — `sales_order_id` or `milestone_id`, `soft_reserve_id`, `status`
- **Invoice** — `party_id`, `invoice_date`, `posting_date` (defaults to `invoice_date`, adjustable — the date the entry lands in an `AccountingPeriod`, distinct from the commercial date on the document), `payment_terms` (credit, cash), `credit_approval_status`, `gross_amount` (pre-VAT value of work), `vat_amount` (computed via `tax_code_id` on `gross_amount` — VAT is charged on the full value of work done, before retention; retention defers payment, not VAT, per §7), `retention_percentage`, `retention_amount` (computed on `gross_amount`, pre-VAT), `net_payable` (what's actually due now: `gross_amount + vat_amount − retention_amount − vat_on_retention − any advance recovery` — the full breakdown the §7 posting needs, not just a retention-only net), `tax_code_id`, `etr_serial_number` (nullable), `etims_invoice_number` (nullable — KRA TIMS/eTIMS submission fields captured at invoice creation now, actual API submission to KRA is a later integration), `status`. The retention and VAT fields apply in both directions — client invoices you raise, and subcontractor bills you receive — since you hold retention on subs the same way clients hold it on you, and both sides charge/bear VAT the same way.
- **InvoiceLine** — `lineable_type`/`lineable_id` (polymorphic — `Invoice`, `CreditNote`, or `DebitNote` all use the same line shape, per KRA's requirement that every fiscal document itemize), `description`, `quantity`, `unit_price`, `line_total`, `vat_amount` (per-line, rounded — see rounding rule below), `source_type`/`source_id` (nullable — traces back to the `SalesOrderLine`/`BOQLine` that generated it, so a line item's origin is never ambiguous). **This was a genuine gap, not a detail** — `Invoice.gross_amount` alone cannot be submitted to KRA TIMS/eTIMS, which requires description/quantity/unit-price/VAT at the line level, and a single-figure invoice can't itemize because there was nowhere for the items to live. **Rounding rule, stated explicitly (real Kenyan VAT practice, and a one-cent discrepancy otherwise breaks Trial Balance reconciliation):** each `InvoiceLine.vat_amount` is computed and rounded independently at the line level; `Invoice.vat_amount` is the **sum of the rounded line-level amounts**, not a separate calculation of `gross_amount × vat_rate` — the two can differ by a cent on multi-line invoices with awkward per-line splits, and per-line-summed is authoritative. Per-line VAT is never backed into from an invoice-level total.
- **CreditNote** / **DebitNote** — `invoice_id`, `amount`, `reason` (dispute, returned_materials, price_adjustment, overbilling_correction, retention_release), `etr_serial_number` (nullable), `etims_invoice_number` (nullable), `note_date`, `posting_date`, `status`. Line items via the same polymorphic `InvoiceLine` above, not a separate line entity — a correction is itemized the same way the thing it corrects was. A credit/debit note is its own fiscal document under KRA TIMS rules — it needs the same ETR/eTIMS fields as `Invoice`, or the transaction it reverses never legally clears. Promoted from backlog to Phase 1: a KRA-numbered invoice can't be corrected by raising a negative invoice (violates numbering rules) or a bare journal entry (bypasses the AR/AP subledger, so the invoice never shows as adjusted). Every correction — disputes, returns after invoicing, price adjustments, overbilling on a progress claim — has to flow through one of these, or `Invoice.status` stops being trustworthy. Retention reversal is proportional, not skipped — see §7.
- **CreditApproval** — `sales_order_id` or `invoice_id`, `requested_amount`, `approved_by`, `approved_at`, `notes`, `status` (pending, approved, rejected, overridden). `Invoice.credit_approval_status` was previously just a status flip with no supporting record — for a Finance-owned control (§11), the approval itself needs to be a traceable record, not something `AuditLog` happens to catch as a side effect of a status change. **Credit limit enforcement, stated explicitly since `Party.credit_limit` previously had nowhere it was actually checked:** at Credit Approval (§2.3), the check is `(sum of net_payable across that Party's open Invoices) + this invoice's net_payable ≤ Party.credit_limit`. Default behavior is **block**, not warn — a Finance user can override via an explicit action, which `CreditApproval.status = overridden` records with the same audit weight as any other approval decision, rather than the limit being silently advisory. **Concurrency, stated explicitly (a real TOCTOU risk, not theoretical):** this check must run inside a transaction holding a row lock on the `Party` (or on a maintained `Party.credit_used` counter updated atomically within the same transaction) — without it, two SalesOrders quoted to the same client simultaneously can both read the same headroom and both pass, since neither sees the other's pending invoice. Same lock discipline already established for `stock_ledger` reservations (§6), applied here to credit.
- **Write-off** — a Phase 1 event, not backlog, in a market where construction clients genuinely do fail mid-project: `Invoice`/`ProgressClaim` reference, `amount`, `reason`, `approved_by`. Posts Dr Bad Debt Expense, Cr Accounts Receivable (§7) — clearing an invoice that will never be collected, distinct from a `CreditNote` (which corrects a billing error) or a `RetentionRelease` (which is money genuinely owed, just not yet due). The full AR/AP document suite (Customer/Supplier Advance beyond what `PaymentAllocation` already covers, formal Debit/Credit memo workflows) stays backlog per §14 — this one event doesn't, since a client's insolvency mid-project with no write-off mechanism leaves Retention Receivable and unpaid milestones sitting on the books indefinitely with no path to clear them.
- **RetentionAccount** — replaces the earlier `RetentionHeld`/single-direction design, which conflated two economically opposite positions. `contract_type`/`contract_id`, `party_id`, `direction` (receivable, payable), `invoice_id` or `progress_claim_id`, `amount`, `released_amount`, `balance` (computed). **A client withholding retention from your invoice is Retention *Receivable* (an asset — money owed to you, just not yet)**; **retention you withhold from a subcontractor's claim is Retention *Payable* (a liability)**. These post to different account types and must never share one table row shape with an implicit direction — the earlier design's "Cr Retention Payable" on every invoice was only correct for the subcontractor-claim direction, not the client-invoice direction, and would have posted the wrong account type on every client invoice raised. Corrected in the ledger table (§7).
- **ContractRetentionTerms** — polymorphic `contract_type`/`contract_id` (SalesOrder or Subcontract — retention terms attach per-contract, never system-wide), `direction` (receivable, payable), `retention_percentage`, `retention_cap` (enforced at posting time: cumulative retention held is checked against the cap on every ProgressClaim/Invoice; once the sum would exceed it, only `cap − cumulative_held` is withheld on that transaction, and once cumulative **equals** the cap — the boundary is inclusive, not "greater than" — all later claims withhold zero until release — never a flat `gross × retention_percentage` applied blindly past the cap), `first_release_trigger` (practical_completion), `second_release_trigger` (dlp_end), `dlp_duration_months`, `release_trigger_source` (own_dlp — subcontract's DLP runs independently and releases on its own schedule; main_contract_dlp — subcontract retention waits on the *Project's* `defects_liability → closed` transition, since the main contractor typically stays on the hook to the client until then, and only then releases the subs). Only meaningful when `contract_type = Subcontract`; a client-side SalesOrder's retention always runs on its own DLP. **Fallback, stated explicitly rather than left implicit:** if `release_trigger_source = main_contract_dlp` but the Project has no `ContractRetentionTerms` of its own (a small direct-sale job, or a project with no client retention clause at all), the system falls back to `own_dlp` behavior using the Subcontract's own `dlp_duration_months` — there's nothing for `main_contract_dlp` to wait on otherwise, and silently never releasing is not an acceptable failure mode.
- **RetentionRelease** — `retention_account_id`, `stage` (practical_completion, dlp_end), `amount`, `released_at`, `status` (pending, blocked_defects, blocked_client_signoff, blocked_dispute, ready, released), `block_reason` (nullable — free text or a linked record depending on `status`). Replaces a single `blocked_by_open_defects` boolean: defects aren't the only reason a release stalls — a client not yet issuing the practical completion certificate, an unsubmitted final account, or an open dispute all block release too, and conflating them into one boolean meant a release could look "unblocked" the moment a defect closed even though a different blocker was still live. Two-stage by design: typically half released at practical completion, the remainder only after DLP defects are verified closed — never a single release event. **`pending → ready` transition trigger, stated explicitly:** a scheduled job re-evaluates all three blocking conditions (open `blocks_retention` `Defect` rows, client sign-off status, open disputes) whenever any of them changes state, and flips `status` to `ready` automatically the moment none apply — not left as a manual status flip someone has to remember to check. A manual override to `ready` remains available — and **is the documented path for early release, not an edge case**: a client asking to release retention before the full DLP has elapsed (10 months into a 12-month DLP, on an off-system agreement) is routine in Kenyan practice, not exceptional. `RetentionRelease` gains an `early_release_reason` field, required whenever a manual override fires before the automatic conditions clear, so the auditor sees explicitly why DLP was skipped rather than finding an unexplained early release.
- **TaxCode** — `code`, `rate`, `account_id`, `type` (vat, withholding). WHT isn't one rate — Kenyan WHT on contractor payments varies by payee (resident with valid certificate: 3%; resident without certificate: 5%; non-resident: 20%). Modeled as **multiple TaxCodes** (`WHT_RESIDENT_3`, `WHT_RESIDENT_5`, `WHT_NONRESIDENT_20`) rather than a rate matrix on one row — simpler to seed, simpler to audit which code a given transaction used. `Party` gets a `tax_residency_status` field (resident_certified, resident_uncertified, non_resident) that determines which `TaxCode` an Invoice/ProgressClaim selects by default. Referenced by `Invoice`, `Payment`, `ProgressClaim`, and `JournalLine` — not a flat `tax_amount` field, since VAT and withholding tax post to different accounts and behave differently (withholding is deducted from what's paid out, not added to what's charged).
- **Payment** — `party_id`, `direction` (receipt, disbursement — §7 uses `Payment` for both money coming in from clients and money going out for subcontractor retention releases and equivalent, and the account posted to flips depending on which: Dr Cash/Bank for a receipt, Cr Cash/Bank for a disbursement; `PaymentAllocation` only applies to receipts settling `Invoice` records — a disbursement against a `ProgressClaim` is tracked via the claim's own `status`, not a `PaymentAllocation` row, since allocation exists to solve the many-invoices-per-payment problem on the AR side and that problem doesn't have an AP-side equivalent here), `reference_type`/`reference_id` (polymorphic, **disbursements only** — links the Payment back to what it paid: a `PurchaseOrder`, a `ProgressClaim`, a `RetentionRelease`, etc., same pattern already used on `StockLedger`. Without this, a "show me all payments against this subcontractor" report has no way to trace a Cash/Bank disbursement back to what it actually settled — **this closes what was previously a missing event entirely: paying a supplier or subcontractor had no ledger posting at all**, only client-side receipts did), `settlement_exchange_rate` (nullable — set only when disbursing against a foreign-currency-denominated `PurchaseOrder`/GRN, §3.4; the rate at payment time, which routinely differs from the GRN's `exchange_rate` and is exactly where FX gain/loss comes from, below), `amount` (actual cash received/paid — never includes any WHT withheld at source), `method` (cash, bank_transfer, cheque, mpesa), `mpesa_reference` (nullable), `mpesa_reconciliation_status` (nullable: unmatched, matched, disputed — actual STK Push/API integration is later, the field and reconciliation status exist now so payment records don't need retrofitting), `bank_account_id` (nullable, §3.10), `tax_code_id`/`wht_amount` (nullable, **`direction = receipt` only** — this is not the subcontractor WHT from §7's Progress Claim posting, which is fully settled at certification and has nothing to do with Payment. This is the reverse case: a *client* withholding tax from what they pay Imara — routine for government and large-corporate clients in Kenya. Set only on Payments *received* where the client's remittance is less than `net_payable` for that reason; the shortfall is a WHT credit Imara can later offset against its own tax bill, not a loss), `received_at`, `posting_date` (defaults to `received_at`, adjustable — a cheque received the 5th might only clear the 12th; the accounting entry follows `posting_date`, not the day the money physically arrived). No `invoice_id` — a single payment routinely settles multiple invoices, part of one invoice, or includes an advance with nothing to allocate against yet. Modeled via `PaymentAllocation` instead.
- **FX gain/loss, a real gap and not just a reporting one, closed here rather than left in backlog with full multi-currency reporting.** A PO booked at 130 KES/USD, paid weeks later at 135 KES/USD, leaves Accounts Payable stated at the GRN's rate while `Payment.amount` (computed at `settlement_exchange_rate`) clears a different KES figure — without a place for the difference to go, AP never actually clears to zero and the Balance Sheet drifts, silently, for every foreign-currency purchase. This isn't full multi-currency accounting (revaluation of open foreign-currency balances at period-end stays backlog, §14) — it's the minimum needed for the ledger to still balance when a single foreign-currency transaction's rate moves between booking and payment. See §7 for the posting.
- **PaymentAllocation** — `payment_id`, `invoice_id` (nullable — null when the amount is an unallocated advance), `amount_allocated`. **Decision: `PaymentAllocation.invoice_id = null` *is* the Customer Advance** — no separate entity — since an advance's whole lifecycle (received, later applied to an invoice, refunded if unused) is just this row's `invoice_id` changing from null to set, or the row getting a `refunded` status. It posts to a dedicated **Customer Advance** liability account (`account_id` on the Chart of Accounts), not generically to Accounts Receivable — until it's allocated to an invoice it isn't revenue-earning AR, it's a deposit owed back. Rules: **overpayment** — the excess stays as an unallocated `PaymentAllocation` row (a Customer Advance), not silently absorbed into the matched invoice; **short-payment** — the invoice's remaining balance stays open, computed as `net_payable` minus the sum of its allocated `PaymentAllocation` rows, no separate "partial" flag needed since it falls out of the arithmetic; **WHT-settled invoices** — where `Payment.tax_code_id` is set (client-withheld WHT on a receipt), the allocation still equals the *cash* amount only, and the WHT portion is recognized separately via the ledger posting in §7 (Dr WHT Receivable / Tax Credit, per the Payment-received row) rather than being folded into `amount_allocated` — an invoice is "settled" once cash-allocated plus WHT-credited equals `net_payable`, not once `amount_allocated` alone does.
- **JournalEntry / JournalLine** — the Shadow Ledger engine (double-entry), written by every module below (§7), never edited directly by module code — always through a posting service. **Correction policy: reversal only, never edit-in-place.** A posted entry that needs correcting gets a new entry with opposite debits/credits posted alongside it — both remain visible, nothing is altered or deleted. This is the audit-grade pattern KRA inspection expects, and it needs to be stated as policy so it isn't quietly relaxed for convenience during implementation. The posting service exposes `reverse(JournalEntry $entry, string $reason)`, called by whichever module triggers a correction (a CreditNote, a cancelled PO whose goods already posted, a payroll run needing correction) — every module that can trigger a correction needs to know it calls this, not a direct edit. Each `JournalLine` carries an optional `analytic_account_id` (§3.7) alongside its normal `account_id`, plus an optional `tax_code_id` (§3.9) so VAT/WHT postings are traceable at the ledger line itself, not just inferred from the source Invoice or Payment. `JournalEntry` also carries `original_intended_posting_date` (nullable) — the field §3.10's `AccountingPeriod` auto-forward rule referred to in prose ("a flag noting the original intended date") without ever naming it; populated only when an entry is forwarded from a closed period, null otherwise.
- **CapitalMovement** — `direction` (loan_received, loan_repaid, capital_injected, capital_withdrawn), `amount`, `party_id` (nullable — a bank/lender for loans, null for an owner's personal capital movements), `movement_date`. The minimal entity the Cash Flow Statement's Financing category (§10.1) needs — previously acknowledged as having "nowhere to map yet," which was accurate for a system with no Loan/Equity entity at all, but not a defensible gap once a first client actually takes a loan or an owner injects capital, which realistically happens in month one for a construction SME, not eventually. Deliberately minimal: no amortization schedule, no interest accrual automation, no cap-table — those stay backlog (§14) — this only gives the Cash Flow Statement's Financing bucket somewhere real to post to, and gives Loan Payable/Owner Capital (§3.1) a source transaction rather than a manual journal entry with no audit trail. **`capital_withdrawn` posts to `Drawings` (§3.1), not `Owner Capital` directly** — standard practice, so contributed and withdrawn capital stay separately visible on the Balance Sheet rather than netting against each other inside one account balance over months of activity.
- **OpeningBalanceBatch** — `as_of_date`, `status` (draft, posted), `posted_by`. The container for a migrating client's historical data load, addressing what was previously described only in prose (§8: "hybrid — sub-ledger reconstruction plus a single opening JournalEntry") with no actual event or entity behind it. Historical `Invoice`, `Payment`, `PaymentAllocation`, `RetentionAccount`, `ProgressClaim`, `Asset`, `AssetDepreciationEntry`, and `StockLedger` rows dated before `as_of_date` are inserted directly (each gaining an `is_opening_balance` boolean so reports and reconciliation can distinguish migrated history from live transactions), and **one** `JournalEntry` with `eventType = opening_balance` (§7) ties the whole batch together, referencing `OpeningBalanceBatch` as `reference_id` — Dr/Cr every account touched by the reconstruction, balanced by Cr/Dr Retained Earnings (Opening) as the plug figure. **`Asset.useful_life_years` semantics, clarified because opening a partially-depreciated asset makes the ambiguity load-bearing:** it is always the *original* total useful life from the asset's actual purchase date, never remaining life — a migrating asset's accumulated depreciation to date is captured explicitly (via an opening `AssetDepreciationEntry`, dated before `as_of_date`, itself part of the batch), and the forward depreciation schedule is computed from `useful_life_years` minus elapsed time, not from a separately-tracked "years remaining" figure that could drift from the original. **Stock opening** is a single valuation layer at one blended unit cost per item as of `as_of_date` — no historical FIFO layers are reconstructed; correct enough for a v1 migration, worth stating so it isn't assumed otherwise. **YTD payroll for P9A continuity**: a client migrating mid-year needs historical `Payslip` rows inserted (also `is_opening_balance`-flagged) for the months already elapsed that year, or `P9A` generation for that year is necessarily incomplete — this is a real migration-data requirement, not optional detail, whenever go-live isn't on a fiscal-year boundary.

### 3.10 Cross-Cutting (Audit, Approvals, Notifications, Compliance)
- **AuditLog** — `user_id`, `action`, `entity_type`, `entity_id`, `old_values`, `new_values`, `ip_address`, `timestamp`. Append-only, built as a Laravel model observer attached to every financial entity (PO, Invoice, Payment, JournalEntry, VariationOrder, RetentionRelease) from the start — this is infrastructure, not a screen, so it isn't phased the way UI is. Financial records are soft-deleted only, never hard-deleted, matching the standard already set on the bookkeeping app.
- **DocumentSequence** — `tenant_id`, `entity_type` (**exhaustive list, not "etc.": `invoice`, `credit_note`, `debit_note`, `purchase_order`, `purchase_requisition`, `goods_receipt_note`, `quotation`, `journal_entry`** — credit and debit notes are fiscal documents under KRA TIMS rules just as strictly as invoices, §3.9, and an "etc." here would leave the seeding migration guessing rather than reading a complete list), `prefix`, `fiscal_year`, `next_number`. **Scoped per tenant, not shared** — this needed stating explicitly, since KRA requires sequential numbering per taxpayer, and a single global PostgreSQL `SEQUENCE` object per `entity_type` shared across every tenant in the database would satisfy uniqueness but not the per-taxpayer sequential requirement. **Decided: a row-locked counter table, not a dynamically-created Postgres `SEQUENCE` per tenant.** A `SEQUENCE` can't be rolled back — a number is consumed the moment it's read, even if the transaction that read it fails, which produces gaps. Legal document numbers need gap control, which is exactly what a `SEQUENCE` structurally can't provide; a counter row locked with `SELECT ... FOR UPDATE` within the same transaction as the document insert gives both concurrency safety and gap control together. **Migrating-client initialization, stated explicitly:** a fresh client starts every `entity_type`'s `next_number` at 1, but a client migrating mid-fiscal-year from an existing system needs each sequence initialized to *one past* their last KRA-issued number for that document type (e.g. their last invoice was `INV-2026-04271`, so `next_number` is seeded at `04272`) — this is a legal continuity requirement, not a convenience default, and is part of the same `OpeningBalanceBatch` migration process (§3.9) as everything else a migrating client brings in. **`fiscal_year` reset rule, stated explicitly:** `DocumentSequence.fiscal_year` resets on the Kenyan tax year (1 January), regardless of a client's own accounting fiscal year if it differs (rare, but legal) — KRA's sequential-numbering requirement is tied to the tax year specifically, and that governs invoice numbering even when it disagrees with the client's internal financial year used for `AccountingPeriod`/reporting. **Numbering format, stated explicitly rather than left to whoever implements it first:** `{prefix}-{fiscal_year}-{next_number, zero-padded to 5 digits}` (e.g. `INV-2026-00001`). Past `99,999` in one fiscal year, `next_number` simply continues to 6 digits (`INV-2026-100000`) — no reset, no separate format; the padding is cosmetic for the common case, not a hard ceiling.
- **AccountingPeriod** — `start_date`, `end_date`, `status` (open, locked, closed). Once the *intended* posting date falls in a `closed` period, the `LedgerPostingService` doesn't reject the entry outright — standard practice is to auto-post it to the earliest currently-open period with a flag noting the original intended date, since outright rejection just pushes finance staff toward off-system workarounds. **Ambiguity resolved, since multiple periods can legitimately be `open` at once (routine during year-end close):** the rule is "auto-forward only when the intended period is not itself open" — if the intended date falls within *any* currently-open period, post there directly, even if it isn't the earliest one; forwarding only kicks in once the intended period has actually moved to `closed`. Reopening a closed period for a correction requires an explicit `AuditLog`-tracked action, not a silent edit. Same category as `AuditLog`: infrastructure that protects data already in the system, built now rather than bolted on after the first closed month gets edited by accident.
- **BankAccount** — `bank_name`, `account_number`, `currency_id`, `gl_account_id`, `status`. Minimal — no statement import or auto-reconciliation yet (that's Phase 2, §14). **Moved to Phase 1 data layer (§8)** — it was previously listed as Phase 2, but the Master Dashboard's Cash Position widget (§10) is Phase 1 and can't compute anything without it; a Phase 1 screen referencing a Phase 2 entity was an inconsistency, not a deliberate sequencing choice. `Payment.method` values (bank_transfer, cheque, mpesa) all implicitly assume a bank account to land in too. `Payment` gains an optional `bank_account_id` once this exists.
- **ApprovalLimit** — `role_id`, `entity_type` (PR, PO, credit_approval, variation_order), `max_amount`, `requires_second_approval_above`, `second_approver_role_id` (nullable, required when `requires_second_approval_above` is set — without this, "second approval" is satisfiable by any second user with the same role, which is a real control gap: a PO above a director-sign-off threshold shouldn't be approvable by two Sales users)
- **Notification** — `user_id`, `type` (reorder_alert, approval_pending, qc_failure, milestone_due, retention_release_due, casual_conversion_due, dlp_ready_to_close, bom_variance_exceeded, hire_invoice_mismatch), `entity_type`, `entity_id`, `message`, `channel` (in_app, email, sms), `sent_at`, `read_at`. **Default channel policy** (SMS costs real money per message via TalkSasa, so this isn't just a UX default): in-app only for internal workflow status changes; email for financial/management notifications (approval pending, milestone due); SMS reserved for field-facing, time-critical alerts (QC failure, reorder trigger) where the recipient likely isn't checking email — configurable per notification type, not per-message. **Digest option, since a busy site genuinely generates enough QC/reorder events to make immediate-SMS-for-everything self-defeating:** lower-priority notification types (reorder alerts, routine QC passes flagged for awareness rather than action) support a `batched_daily`/`batched_weekly` delivery mode alongside `immediate` — one summary message instead of twenty separate ones — while genuinely urgent types (QC failure blocking a certification, retention release ready) always stay immediate regardless of the recipient's digest preference. Without this, high message volume trains recipients to mute the channel, and a real alert gets missed alongside the noise. `dlp_ready_to_close` routes to the Project Manager role by default (configurable), since "someone signs off" needs an actual someone. SMS channel reuses the existing TalkSasa infrastructure already wired for ImaraPay/ImaraConnect.
- **IdempotencyKey** — `key` (unique, tenant-scoped), `endpoint`, `response_payload` (nullable — filled once the original request completes), `created_at`. §1.1 mandates idempotency tokens on financial-mutation frontend requests and on every inbound webhook, but named no table to actually store them in — this is that table. A repeated request with the same key returns the stored `response_payload` rather than re-executing the mutation; a key with no stored payload yet (the original request is still in flight) is a duplicate-in-progress, handled the same way as the webhook-before-commit case in §1.1. Cheap to add now, materially more painful to retrofit once double-posted payments already exist in production data.
- **ComplianceDocument** — `party_id` (subcontractor), `document_type` (insurance, lien_waiver, safety_cert, tax_compliance), `issue_date`, `expiry_date`, `file_path`, `status` (valid, expiring_soon, expired). **Blocking point, stated explicitly: `ProgressClaim.status` transitioning to `certified`** — not at payment. Certification is where the claim becomes a real liability (it's what posts to the ledger, §7); blocking after certification but before payment would leave an approved liability sitting in limbo with nowhere to go. **Required set, stated explicitly rather than left as an unstated global assumption:** the certification check reads `Subcontract.required_document_types` (§3.4) for that specific subcontract, not a hardcoded list applied identically to every subcontractor — a small supply-only subcontract and a large structural package legitimately need different document sets. **Expiry boundary, stated explicitly:** `expiry_date` is the last valid day, inclusive — a document expiring 30 June is still `valid` for certification actions occurring on 30 June itself, and becomes `expired` starting 1 July, not at some ambiguous point during the expiry day.

### 3.11 HR & Payroll
A full module, not a Phase 3 stub — covers full-time, part-time, and casual staff, Kenyan statutory compliance, and posts into the same Shadow Ledger as every other module.

- **Employee** — `resource_id` (nullable — links back to §3.6 when the employee is also project-assignable), `employee_number`, `id_number`, `kra_pin`, `nssf_number`, `shif_number`, `helb_account_number` (nullable), `employment_type` (full_time, part_time, casual, contract), `date_of_hire`, `date_of_exit` (nullable), `cumulative_casual_days_worked` (nullable — running count, only tracked for `casual`; see below), `status` (active, probation, notice_period, terminated). **No `on_leave` status** — leave is a state derived from `LeaveRequest`, not a parallel flag on Employee; an employee on annual leave is still actively employed, and duplicating that onto `status` creates two sources of truth that will drift (a `LeaveRequest` gets approved but `Employee.status` isn't updated, or vice versa).
- **EmploymentContract** — `employee_id`, `contract_type`, `pay_frequency` (monthly, weekly, daily), `basic_salary` (nullable — full-time/monthly staff), `hourly_rate` / `daily_rate` (nullable — part-time/casual staff, mutually exclusive with `basic_salary`), `overtime_multiplier_weekday` (default 1.5, per Employment Act 2007), `overtime_multiplier_restday` (default 2.0), `start_date`, `end_date` (nullable). **Non-overlap enforced** — a promotion or contract-type change means the old contract's `end_date` is set and the new one's `start_date` begins the next day; the system refuses a second contract on the same employee with overlapping active date ranges, since two simultaneously-active contracts leaves a `Timesheet` on an overlap date with no unambiguous rate to apply.
- **Timesheet** — `employee_id`, `date`, `hours_normal`, `hours_overtime_weekday` (nullable), `hours_overtime_restday` (nullable — separate from `hours_normal` rather than a single total, since Kenyan overtime pay is a different rate, not a flat extension of the normal rate), `project_id` (nullable), `approved_by`, `status` (submitted, approved, rejected). Where `project_id` is set, hours feed both payroll calculation *and* the project's `analytic_account_id` (§3.7) — labour cost lands on the right project automatically instead of being allocated after the fact.
- **PublicHoliday** — `date`, `name`, `is_paid` (Kenyan public holidays are paid for employees who'd otherwise have worked) — without this, daily-rate payroll needs a manual adjustment every holiday month; with it, `PayrollRun` generation reads the calendar directly. **Seed data, stated as a required Phase 1 deliverable, not assumed:** the current and next calendar year's Kenyan public holidays must be seeded before the first payroll run — this is ordinary reference data, not something a client should have to enter manually before they can pay staff.
- **LeaveType** — `name` (annual, sick, maternity, paternity, unpaid), `days_entitled_per_year`
- **LeaveRequest** — `employee_id`, `leave_type_id`, `start_date`, `end_date`, `status` (pending, approved, rejected)
- **StatutoryDeductionRate** — `deduction_type` (paye, nssf, shif, housing_levy, helb, nita), `effective_from`, `rate_bands` (JSON — PAYE is banded, not flat; NSSF has tiers; NITA is a flat employer-side levy, currently KES 50/employee/month), `employer_rate_bands` (JSON, nullable — NSSF and Housing Levy both have an employer-matched portion in addition to the employee deduction; where a `deduction_type` has no employer portion, this stays null and `Payslip`'s corresponding employer field is zero) — kept as data, not hardcoded logic, since these change on government policy, not on a release cycle. **NITA is entirely an employer cost, not an employee deduction** — it never appears on `Payslip` as a deduction, only as an employer expense on the `PayrollRun` posting (§7). **Seed data, stated as a required Phase 1 deliverable:** current PAYE bands, NSSF tiers, SHIF rate, Housing Levy rate, HELB schedule, and the NITA amount must be seeded before the first payroll run — without this, that first run either fails outright or requires manually entering a rate per employee, defeating the point of the data-driven design.
- **PayrollRun** — `period_start`, `period_end`, `status` (draft, processing, approved, paid), `run_date`
- **Payslip** — `payroll_run_id`, `employee_id`, `gross_pay` (includes computed overtime pay), `taxable_pay` (defaults to `gross_pay` unless non-taxable allowances are introduced later, in which case they're excluded here — feeds P9A/P10 directly rather than those reports assuming taxable pay always equals gross), `days_paid_not_worked` (leave days and paid public holidays in the period, from approved `LeaveRequest` and `PublicHoliday` — for monthly-salaried staff this doesn't change `gross_pay` since salary is fixed regardless, but for daily-rate/casual staff it's a real pay component with no corresponding Timesheet entry, since nobody logs hours on a day they didn't work), `paye_amount`, `personal_relief_applied`, `nssf_amount` (employee portion), `shif_amount`, `housing_levy_amount` (employee portion), `helb_amount`, `other_deductions`, `employer_nssf_amount`, `employer_housing_levy_amount` (the employer-matched portions — separate fields, not netted against the employee figures, since they post to a different Dr line in §7: an expense to the company, not a deduction from the employee), `net_pay`, `status`. For part-time/casual staff, `gross_pay` is computed from approved Timesheets (hours actually worked) plus `days_paid_not_worked` at the contract's `daily_rate`, against `EmploymentContract.hourly_rate`/`daily_rate` (plus overtime multipliers) rather than a fixed `basic_salary`.
- **P9A** — `employee_id`, `year`, cached annual summary (`taxable_pay` — not just `gross_pay`; the Kenyan P9A Tax Deduction Card requires taxable pay specifically, and if all pay is taxable this equals `gross_pay`, but the field needs to exist separately rather than be assumed identical, since non-taxable allowances would otherwise have nowhere to be excluded, `total_paye`, `personal_relief_applied` — a fixed statutory amount, but stated per employee-year for audit traceability rather than recomputed from a constant at filing time) for the statutory Tax Deduction Card, generated from the year's Payslips rather than recalculated ad hoc at filing time. `Payslip` gains a matching `taxable_pay` field (defaults to `gross_pay` unless non-taxable allowances are introduced later) so P9A generation has a real source rather than assuming gross and taxable pay are always the same thing.
- **P10** — `month`, `year`, cached employer-level monthly PAYE return summary across all Payslips in that period's PayrollRuns. **HELB is filed separately, not merged onto the P10 form** — HELB has its own remittance schedule and portal; P10 covers PAYE only. Tracked in this system for completeness and reconciliation, but the earlier "filed alongside PAYE" phrasing was loose enough to mislead an implementer into building it onto the P10 output.
- **StatutoryRemittance** — `period`, `authority` (KRA-PAYE, NSSF, SHIF, HELB, NITA, KRA-WHT), `amount`, `reference_number` (the payment reference from the authority's portal), `paid_at`, `status`. **Closes a real gap**: every `PayrollRun` and every subcontractor WHT posting (§7) creates a payable to one of these authorities, and nothing in the model previously reduced it — the Balance Sheet would overstate these liabilities by the full cumulative amount since go-live, growing every month. This is what the "Net pay disbursed" row already does for `Net Pay Payable`; the same clearing pattern was missing for every other statutory payable.

**Casual-to-permanent conversion (Employment Act 2007, s.37):** a casual employee working one month continuously, or an equivalent of three months with breaks, converts to permanent status with full statutory benefits — treating a converted employee as still-casual is a real compliance risk (back-benefits owed). `Employee.cumulative_casual_days_worked` increments from approved Timesheets; when it crosses the statutory threshold, a `Notification` (§3.10, type `casual_conversion_due`) fires to HR. Conversion itself stays a manual action on the Employee record (change `employment_type` to `full_time`, create a proper `EmploymentContract`) — not automatic, since the manager should confirm the employment pattern actually qualifies rather than the system silently reclassifying someone. **Mid-period conversion, stated explicitly:** conversion takes effect the day *after* the threshold is reached, and if that falls mid-payroll-period, `PayrollRun` generates **two `Payslip` rows** for that employee that period — one under the old `EmploymentContract` (casual rates, days worked to the conversion date), one under the new (permanent rates, from conversion to period end) — rather than one blended row trying to average two different pay structures.

**Final settlement on termination:** `EmploymentContract.date_of_exit` triggers a **`FinalSettlement`** — `employee_id`, `last_working_day`, `days_worked_this_period`, `accrued_leave_days`, `leave_encashment_amount` (nullable — only if the contract/company policy allows cashing out unused leave rather than forfeiting it), `final_paye_amount`. Prorates the terminating month's salary to `days_worked_this_period` rather than paying a full month, and computes leave encashment against `LeaveType.days_entitled_per_year` less days already taken. Without this, terminating an employee mid-month either overpays a full month or forces manual proration that defeats the point of a payroll module.

**Ledger integration:** each `PayrollRun`, once approved, posts through the same `LedgerPostingService` as everything else — see §7 for the exact split (one `JournalLine` per project an employee's Timesheets touched that period, not one blended line per PayrollRun, so per-project labour cost in `AnalyticAccount` rollups is accurate down to actual hours worked, not an estimate).

**Scope note:** this is the data layer and the PAYE/NSSF/SHIF/Housing Levy *reports* (P9A, P10) — the actual KRA/NSSF/SHIF online filing submission (API integration) stays with the KRA iTax integration already scoped for later (§8), same relationship as ETR fields existing on Invoice now while the TIMS API submission comes later.

### 3.12 Fixed Assets & Plant/Equipment
Promoted from backlog — combined into one module per the earlier recommendation, since owned plant is simultaneously a fixed asset and a project-assignable resource. Derived from the Sali Assets & Inventory Management system (deployed as both SaliAssets and ABCAMI) rather than designed from scratch — that system's depreciation engine is proven across real client data, and its data model is the starting point here, generalized and, critically, **wired into the Shadow Ledger from the start** — which Sali Assets itself doesn't do (its own roadmap explicitly frames ERP integration as a gap: "ERP syncs financial data; AMS holds physical asset truth"). Imara doesn't have that gap, since it's the ERP.

- **Asset** — `asset_number`, `name`, `category_id` (`AssetCategory`), `asset_type` (fixed_asset, plant_equipment — distinguishes static assets like office furniture from project-assignable equipment like an excavator; both depreciate the same way, only the latter gets `AssetAssignment` records), `serial_number`, `location_id`, `custodian_party_id` (nullable — current holder, mirroring Sali Assets' check-in/check-out custody model), `date_of_purchase`, `purchase_cost`, `residual_value` (kept as its own field, deliberately never conflated with accumulated depreciation — see below), `useful_life_years` (mutable — Sali Assets supports lifespan changes mid-life, e.g. a revaluation extending an asset's remaining life; a `lifespan_change_reason` is logged via `AuditLog` when it changes, not silently overwritten), `depreciation_method` (straight_line, sum_of_digits, diminishing_balance — the three methods already proven in Sali Assets, not reinvented), `warranty_years` (nullable), `status` (in_use, under_maintenance, disposed, written_off)
- **AssetComponent** — `asset_id` (parent), same depreciation fields as `Asset` (`purchase_cost`, `useful_life_years`, `depreciation_method`, `residual_value`) but scoped to one component of a composite asset. Total depreciation for the parent is the sum of its components' depreciation, not one blended schedule — this is the componentised-asset pattern already built and proven in Sali Assets (a building's structure and its M&E fit-out depreciate on genuinely different schedules), worth preserving rather than flattening into a simpler model.
- **AssetDepreciationEntry** — `asset_id` (or `asset_component_id`), `period`, `depreciation_amount`, `accumulated_depreciation`, `net_book_value`. Generated by a scheduled monthly job (§1), one entry per asset per period — this is what actually posts to the ledger (§7) and what the Balance Sheet's Fixed Assets figure is computed from.
- **AssetRevaluation** — `asset_id`, `revaluation_date`, `net_book_value_at_revaluation` (**stored, not recomputed on read** — captured once at the moment of revaluation as `purchase_cost − accumulated_depreciation_to_date`, correctly computed this time, not left to default to zero — this is the exact bug the Sali Assets code audit caught: the revaluation record was setting this field to `purchase_cost − purchase_cost`, always zero, because the subtraction used the wrong value. Stored rather than computed-on-read deliberately, since it's a historical snapshot — depreciation continues to accrue after the revaluation date, so recomputing it later from current `accumulated_depreciation` would give a different, wrong answer for what NBV *was* at that point in time), `accumulated_depreciation_at_revaluation` (**its own field, separate from `residual_value`** — the other half of that same bug was storing accumulated depreciation in the field meant for scrap/residual value; those are never the same number and must never share a column), `new_valuation`, `new_residual_value`, `new_useful_life_years` (nullable — a revaluation can also reset remaining life), `reason`, `approved_by`
- **AssetDisposal** — `asset_id`, `disposal_date`, `disposal_type` (sold, scrapped, written_off), `sale_proceeds` (nullable), `net_book_value_at_disposal` (**stored, captured at disposal time** — `purchase_cost − accumulated_depreciation_to_date` as of `disposal_date`, same immutability rationale as `AssetRevaluation.net_book_value_at_revaluation`: this is a historical snapshot, and computing it later from current `accumulated_depreciation` would give a different, wrong answer since depreciation stops accruing after disposal but the "current" figure wouldn't reflect that stop-date), `gain_loss_amount` (computed: `sale_proceeds − net_book_value_at_disposal`), `status`
- **AssetAssignment** — `asset_id` (where `asset_type = plant_equipment`), `project_id`, `assigned_date`, `released_date` (nullable), `internal_daily_rate` (what the project is charged for using owned equipment — distinct from the asset's purchase cost, this is what makes "project cost = labour + material + subcontract + equipment" actually work), `meter_reading_start`/`meter_reading_end` (nullable — hour/km-based usage tracking, a lighter version of Sali Assets' full check-in/out flow, enough to catch gross discrepancies without building the whole mobile check-in workflow yet)
- **EquipmentHireContract** — for *hired-in*, non-owned plant: `party_id` (hire company), `description`, `project_id`, `hire_rate`, `hire_start_date`, `hire_end_date` (nullable), `expected_days` (computed from the assignment dates). When the hire company's invoice/PO line claims a different number of days than `expected_days`, that's the discrepancy check flagged earlier as the actual margin risk on hired plant — worth surfacing as a Notification (`hire_invoice_mismatch`) rather than requiring someone to remember to check by hand.

**Ledger integration** (§7 has the full posting table): acquisition capitalizes to the Fixed Assets account; each `AssetDepreciationEntry` posts Depreciation Expense against Accumulated Depreciation — **company-wide, never `analytic_account_id`-tagged, regardless of whether the asset is assigned to a project**, since depreciation reflects the asset's own book value declining, not project costing. The project-facing cost instead comes from a separate mechanism: `AssetAssignment.internal_daily_rate` posts its own periodic entry (Dr Project Equipment Cost, tagged with the project's `analytic_account_id`; Cr Internal Equipment Recovery, a contra-expense account) — this is what actually makes owned-equipment cost show up in project P&L. The two are deliberately separate postings, not one tagged version of the other: if depreciation were *also* analytic-tagged, a project would be double-charged for the same equipment — once via depreciation, once via the internal rate. Revaluation posts to a Revaluation Reserve (upward) or P&L (downward, unless reversing a prior upward revaluation — standard treatment); disposal clears the asset and accumulated depreciation and posts the resulting gain or loss. New `ChartOfAccounts` entries needed: Fixed Assets at Cost, Accumulated Depreciation (contra-asset), Depreciation Expense, Internal Equipment Recovery, Asset Revaluation Reserve, Gain/Loss on Disposal — none of this exists as generic "seeded per entity" accounts currently, it needs to be added to the standard seed.

## 4. Supply Path Decision — where it's set and what it drives

`supply_path` is set once, at Quotation/SalesOrder creation, and determines:
- Which FG-availability check fires (against existing stock vs. against a BOM/BOQ-driven production requirement)
- Whether Billing is single-invoice or milestone-based
- Whether a Project and Milestones get created at all

This should be a first-class enum on `sales_orders`, not inferred at runtime — every downstream module branches on it.

---

## 5. State Machines

### 5.1 SalesOrder
This is the **Direct Sale / Manufacture-for-Sale** path only:
```
draft → feasibility_check → (rejected → [end] | renegotiating → feasibility_check)
      → approved → awaiting_fg → in_fulfillment
      → partially_delivered (one or more DeliveryLines posted, some SalesOrderLines still short)
      → delivered (all lines fully covered) → billed → closed
```
`partially_delivered` mirrors `PurchaseOrder`'s `partially_received` state (§5.2, §3.4) — a `SalesOrder` isn't forced to either stay `in_fulfillment` (wrong, some goods have shipped) or jump straight to `delivered` (wrong, more is still owed) when a shipment only covers part of what was ordered.
**Project and Manufacture-for-Project supply paths follow a different terminal path** — there's no `delivered` state, since §2.1's flow routes through Labour → Project → Milestones instead of the Delivery Process, and billing happens per milestone rather than once. For these, `approved → awaiting_fg → in_fulfillment` still applies, but the SalesOrder's `closed` is gated by `Project.status = closed` (§5.4), not by a delivery event. Building the state machine exactly as drawn above for *every* supply path would leave Project-path orders stuck in `in_fulfillment` indefinitely, since they never hit a `delivered` transition.

### 5.2 PurchaseOrder
```
requisitioned → pending_approval → approved → ordered
             → partially_received (one or more GRNLines posted, some PurchaseOrderLines still short) → received (all lines fully covered)
             → quarantined → (qc_passed → stocked | qc_failed → returned)
```
`partially_received` added per §3.4's `PurchaseOrderLine`/`GRNLine` design — a PO isn't forced to either stay "ordered" (wrong, goods have arrived) or jump straight to "received" (wrong, more is still owed) when a delivery only covers part of what was ordered.

### 5.3 StockReservation
Operates on two orthogonal fields on `SalesOrderReservation` (§3.2), not one combined state:
```
reserve_type (commitment level):  soft → hard
status (lifecycle):               active → consumed
                                        → released (on order cancellation or renegotiation)
```
A reservation escalating from soft to hard is a `reserve_type` change; it stays `status = active` throughout. `status` only moves once the reservation's life actually ends — consumed by an issue, or released back to availability.

### 5.4 Project / Milestone
```
Project: initiated → in_progress → complete → defects_liability → closed
                                              → cancelled (terminal, from any pre-closed state)
Milestone: pending → utilized → signed_off → rework_required → invoiced → closed
```
`defects_liability` is a real state, not a formality — the second-stage `RetentionRelease` (§3.9) is blocked from firing while any `Defect` (§3.7, `blocks_retention = true`) on the project is `open` or `in_progress`, and `Project` only reaches `closed` once that release has actually happened. The `complete → defects_liability` transition itself is scheduled: a job checks `ContractRetentionTerms.dlp_duration_months` against `complete`'s date and flags the project as DLP-eligible-for-review, but `defects_liability → closed` stays a manual confirmation, not an automatic transition — the system surfaces "ready to close" (no blocking defects, DLP elapsed) as a Notification and dashboard item, someone still signs off. Fully automatic closure risks a project silently closing before a client-side issue that never made it into the system gets raised. **Race condition, stated explicitly:** the same scheduled job re-evaluating DLP eligibility can fire moments after a Finance user has already manually marked the project ready-to-close, acting on stale data and re-triggering a release that's already in motion. `Project` gains a `version` column (optimistic locking) — the job checks the current version before acting and re-reads if it's changed since the job started, rather than assuming its own view of the project is still current. **`cancelled` added as a terminal state, previously entirely unhandled:** reachable from any pre-`closed` state, for when a client cancels a project outright. Documented handling for open obligations at cancellation: open `Subcontract`/`ProgressClaim` rows are settled or disputed per their own status (not silently abandoned), any `RetentionRelease` in `pending`/`blocked_*` status requires an explicit early-release decision (§3.9's `early_release_reason` applies here too), open `PurchaseOrder`s against the project are cancelled or, if goods already delivered, received against normally, and any unbilled `Milestone`s are written off via the same mechanism as an uncollectable invoice (§3.9's `Write-off`) rather than left in limbo.

## 6. Cross-Module Data Contract — Stock & Reservations

This is the piece flagged earlier as expensive to retrofit, so it's fixed here rather than left to each module to decide independently:

- **No module writes directly to an `items.stock_on_hand` column.** Every *physical* stock change that has cleared into available/owned stock — QC-passed GRN receipt, production consumption/output, scrap write-off, surplus return, transfer — is an insert into `stock_ledger`. Available quantity is always a computed sum, not a stored field. **Goods arriving against a PO are not a `stock_ledger` event at all until QC passes** — a GRN receipt first inserts into `StockQuarantine` (§3.3), and only a *passed* QC disposition triggers the `stock_ledger` insert; a *failed* disposition and subsequent return to supplier never touch `stock_ledger` at all. This is deliberate, not just consistent phrasing: since availability is computed purely from `stock_ledger`, and quarantined/failed goods never enter it, they're structurally unable to be reserved, issued, or sold — no separate "block" check is needed anywhere else in the system, the absence from the ledger *is* the block.
- **Reservations are their own state and their own table** (`SalesOrderReservation`, soft/hard), never a `stock_ledger` movement type — a reservation isn't a physical fact, it's a commercial commitment. Soft reserve reduces *available-to-promise*, not physical stock. Hard reserve reduces available stock in the availability computation without an actual physical movement having happened yet. This split (borrowed from a review that correctly flagged the earlier design's mixing of the two) keeps physical inventory accounting and commercial commitment cleanly separable — necessary once real financial statements depend on `stock_ledger` alone reflecting physical reality.
- **Reorder Level checks read the same ledger** — a scheduled job (or a ledger-insert trigger) compares computed on-hand against `items.reorder_level` and raises a `DemandTrigger` automatically, matching the dashed "Reorder Level" line in the flowchart.
- **The availability board (Phase 2 UI) is a read-only view over `stock_ledger` + active reservations** — it doesn't need its own data model, only a live/polling read layer once built.
- **Valuation is computed, not stored, per the item's category `valuation_method`** — a FIFO category walks the ledger oldest-first to cost an issue; a weighted-average category recalculates a running average on each receipt. `stock_ledger.unit_cost` is the raw input. **Valuation method changes are effective-dated, never retroactive** — switching a category's method applies going forward only; historical valuation layers are immutable, since retroactively recalculating them would silently change already-reported inventory value, COGS, and gross profit on closed periods.
- **Reservation writes happen inside a transaction with a pessimistic lock** (`SELECT ... FOR UPDATE` on the relevant `stock_ledger` rows for that item/warehouse) — not urgent for a small initial team, but the reservation code needs to be written this way from the start, since retrofitting transaction boundaries around a read-then-insert pattern after concurrent users start hitting it is far more painful than writing it correctly once. **Edge case: the very first reservation against an item has no existing `stock_ledger` rows to lock.** Lock the `Item` row itself (or use a Postgres advisory lock keyed on `item_id`/`warehouse_id`) for that case rather than assuming rows always exist to lock. **Check-and-reserve is one transaction, not two statements** — the availability computation and the reservation write happen inside the same locked transaction, never a "check availability" read followed by a separate "reserve" write; a check that happens outside the lock can see a stale on-hand figure that's already changed by the time the reservation is written moments later.

This contract means Manufacturing, Procurement, and Sales can all be built independently as long as each obeys this one rule — the live board becomes a UI-only addition later, not a schema change.

## 7. Shadow Ledger Integration Points

Every one of these posts a journal entry via a single `LedgerPostingService`, never ad hoc. Where a Project is involved, the posting also carries `analytic_account_id` (§3.7) so per-project P&L is a query, not a report-building exercise:

| Event | Journal effect |
|---|---|
| Opening balance (`OpeningBalanceBatch` posted, §3.9) | One posting per migrating client, tying the whole historical-data-load batch together. Dr/Cr every account touched by the sub-ledger reconstruction (Fixed Assets at Cost and Accumulated Depreciation for migrated assets, Inventory at the opening blended unit cost, Accounts Receivable/Payable and Retention Receivable/Payable for open invoices and claims, Cash/Bank for opening balances), balanced by Cr/Dr **Retained Earnings (Opening)** as the plug figure — not Revenue or Expense, since none of this is current-period activity. Every migrated sub-ledger row (`Invoice`, `Payment`, `PaymentAllocation`, `RetentionAccount`, `ProgressClaim`, `Asset`, `AssetDepreciationEntry`, `StockLedger`) carries `is_opening_balance = true` so this posting and the records it reconstructs can always be traced back to each other. |
| GRN goods receipt (QC passed) | Dr Inventory (RM) at `stock_ledger.unit_cost`, Cr Accounts Payable. **Which unit cost feeds `stock_ledger`, stated explicitly per `Category.valuation_method`:** for `fifo`/`weighted_average`, `stock_ledger.unit_cost` is the actual GRN cost, and this row is the whole posting. For **`standard_cost`, see the row immediately below — the posting is different, not just the input value.** |
| GRN goods receipt, standard-cost category (QC passed) | **Previously undefined — `Item.standard_cost` (§3.1) was seeded and `Category.valuation_method` offered the option with no §7 row behind it, the same class of gap this document's earlier passes were built to catch.** Dr Inventory (RM) at `Item.standard_cost × quantity` (`stock_ledger.unit_cost` is the *standard* cost for this category, not actual — the whole point of standard costing is that inventory carries a stable value regardless of what any one purchase happened to cost), Cr Accounts Payable at the *actual* GRN cost, Dr/Cr **Purchase Price Variance** for the difference: Dr (unfavorable) when actual exceeds standard, Cr (favorable) when actual is below it. `standard_cost` itself never changes as a side effect of a single purchase — only via an explicit cost-revision action (§3.1). |
| GRN return to supplier (QC failed) | Reverse the above |
| Post-acceptance supplier return (stock already passed QC, returned later — over-order, wrong spec, storage damage) | Distinct from the row above, which is specifically the QC-failure path. Dr Accounts Payable (unpaid stock, reducing what's owed) or **Dr Accounts Receivable** (already-paid stock — the supplier now owes a refund/credit; the same account used for any amount owed back to Imara, even though the debtor here is a supplier rather than a customer), Cr Inventory (RM) at the ledger's recorded `unit_cost` — the same `StockLedger.movement_type = 'return'` value already defined (§3.3), previously modeled with no posting behind it. |
| Landed cost allocation (freight/duty/clearing) | Dr Inventory (RM), Cr **Landed Cost Payable** (§3.1 — one consolidated account, not one per `cost_type`) — allocated across the GRN's line items proportionally, so imported RM cost reflects true landed cost, not just supplier invoice price. The per-`cost_type` breakdown (which portion was freight vs. duty vs. clearing) isn't carried on the `JournalLine` itself — `JournalLine` only has `analytic_account_id`/`tax_code_id`, no memo field — it lives on the source `LandedCost` record, reachable via this posting's `reference_id`. |
| Production consumption (RM → FG) | Dr Inventory (FG) / Cr Inventory (RM) at the RM's computed valuation cost, plus wastage variance if actual ≠ BOM allowance |
| Rework/Scrap write-off | Dr Scrap/Variance expense, Cr Inventory (FG) |
| Proforma → Soft Reserve | No posting (memo only) |
| Credit Approval granted | No posting — gates the next step |
| Invoice raised, client contract (per `invoice_policy`: on_order, on_delivery, or on_milestone) | VAT is charged on the full value of work done, before retention — retention defers *payment*, not VAT. **`net_payable` already includes VAT on the non-retained portion** (§3.9's formula: `gross_amount + vat_amount − retention_amount − vat_on_retention − advance_recovery`), so it's posted as-is, not with VAT added a second time. Dr Accounts Receivable at `net_payable`, Dr Customer Advance at `advance_recovery` (when applicable — clears the liability previously booked when the advance was received, §3.9), Dr Retention Receivable at `retention_amount + vat_on_retention`, Cr Revenue at `gross_amount`, Cr VAT Payable at `vat_amount`, tagged with `analytic_account_id` when a Project is attached. *(Worked example: gross 100, VAT 16, retention 10% → retention_amount 10, vat_on_retention 1.6, net_payable 104.4. Dr AR 104.4 + Dr Retention Receivable 11.6 = 116. Cr Revenue 100 + Cr VAT Payable 16 = 116. Balances.)* |
| Progress Claim certified, subcontract | Dr Subcontract Expense at `amount_certified` (gross — the full cost is incurred at certification, not the net; the unpaid portion is a liability split, not an expense reduction), Dr VAT Input/Receivable at `vat_amount` (**not** VAT Payable — the subcontractor is charging VAT to the main contractor here, so this is input VAT the main contractor can reclaim, the reverse direction of the client-invoice row above). Cr Accounts Payable at `net_payable` (§3.4's formula: `amount_certified + vat_amount − retention_amount − vat_on_retention − wht_amount`), Cr Retention Payable at `retention_amount + vat_on_retention`, Cr WHT Payable at `wht_amount` — **WHT is recognised here, at certification, not at payment**; there's no separate WHT posting at Payment. Where certification is partial (`amount_certified` < `amount_claimed`), the expense is the certified gross amount, not the net. *(Worked example: certified 100, VAT 16, retention 10% → 10, vat_on_retention 1.6, WHT 3% → 3, net_payable 101.4. Dr Expense 100 + Dr VAT Input 16 = 116. Cr AP 101.4 + Cr Retention Payable 11.6 + Cr WHT Payable 3 = 116. Balances.)* |
| Progress Claim reversed (`status = reversed`, disputed after certification) | Exact mirror of the certification posting above — Cr Subcontract Expense, Cr VAT Input, Dr Accounts Payable, Dr Retention Payable, Dr WHT Payable, all at the original certified amounts, referencing the original `ProgressClaim`. Uses the same `reverse()` mechanism as every other correction (§3.9) — this was a missing *trigger*, not a missing *mechanism*: real subcontracts get certified one month and disputed the next after a failed inspection, and without this the disputed AP and project cost sit on the books indefinitely. |

Never a negative invoice (KRA numbering rules don't allow it); carries its own `etr_serial_number`/`etims_invoice_number` (§3.9) since a credit note is itself a fiscal document under KRA TIMS rules. |

The credit-note-only path can't do this second half; a return that never adjusts inventory leaves stock permanently understated. |

| Retention released — client side (practical completion or DLP end) | Dr Cash/Bank, Cr Retention Receivable — only posts once `RetentionRelease.status = ready` (§3.9). **Resolved: always a cash-receipt posting, never a fresh Invoice.** VAT on the retained amount was already charged at the time of the original invoice (`vat_on_retention` is part of `Retention Receivable`'s balance from day one, §7's Invoice-raised row) — invoicing the release separately would recognize the same VAT a second time. If a client's own process requires a formal document acknowledging the release, that's an administrative record, not a ledger event; `postRetentionReleasedClient` posts one way, always. |
| Retention released — subcontractor side | Dr Retention Payable, Cr Accounts Payable (or Cash/Bank on disbursement) — same status-gate, mirrored direction |
| Variation Order approved | **No ledger posting — memo only, resolved on review (v10).** The row previously here ("Dr/Cr Revenue... same posting shape as the original Quotation") was ambiguous enough that two independently-defensible readings existed — one mirroring the Invoice-raised shape (Dr AR/Retention Receivable, Cr Revenue/VAT Payable), one booking to an intermediate "Unbilled Contract Value" account — and neither is actually correct. Recognizing Revenue at VO-approval time, before any work covered by the delta has been invoiced, is premature/WIP-style revenue recognition — which contradicts this document's own explicit deferral of percentage-of-completion accounting (§8, §14: "held back past Phase 3, needs proven cost data first"). A VO is a contract-value amendment, not a billing event: §3.7 already has it mutate `BOQLine`/`BOQSection` and recalculate `BOQ.revised_contract_value`; the delta becomes billable through the *same* mechanisms as any other BOQ line — the next `Invoice raised` (on_order/on_delivery) or `Milestone` reaching `signed_off`/`invoiced` (on_milestone) — and that posting already recognizes revenue correctly, at the right time, with no VO-specific ledger logic needed. |
| `VariationOrderReversal` posted (an approved VO later cancelled) | Also memo-only, same reasoning as above — reverts `BOQ.revised_contract_value` and any not-yet-`billing_locked` Milestone's `billing_amount`, with no ledger posting of its own, since the original approval never posted one either. |

Any unallocated excess posts Cr Customer Advance instead of sitting unposted. This is the one role `Payment.tax_code_id`/`wht_amount` actually serves — it has nothing to do with subcontractor WHT, which is fully settled by the time Payment exists. |

This is the minimum needed for AP to actually clear on a foreign-currency purchase when the rate moves between GRN and payment — not full multi-currency revaluation, which stays backlog (§14). |

Both sides reduce to `gross_pay + employer_statutory_total + nita_amount`. Balances by construction, for any values.)* |

## 8. Module Scope & Build Order — revised

The original MVP phasing (Finance / CRM & Sales / Inventory / Procurement first, Manufacturing and Projects in Phase 2) was set before this flowchart existed. **The flowchart shows these aren't actually separable at the data layer** — Direct Sale itself depends on the FG-availability check, which depends on Manufacturing's BOM logic existing in some form, and Procurement's Demand Trigger can originate from Manufacturing. A Direct-Sale-only v1 with no Manufacturing at all would need to either hardcode "FG always available" (defeats the purpose) or stub the FG check — worth deciding explicitly rather than discovering mid-build.

**Recommended revised approach:** build the *data layer and state machines* for all modules together (they're one interconnected workflow), but phase the *screens*. A second cut through this same list, specific to the construction-industry additions: retention, tax, and multi-warehouse **must** be in the Phase 1 data layer, not deferred, because each one changes the schema of a table that will already hold live data by the time it's revisited — retention restructures every Invoice, tax is required to post a valid journal entry at all, and adding `warehouse_id` after `stock_ledger` is already the busiest table in the system means migrating live records instead of seeding a default.

**Phase 1 data layer (all of it — schema and state machines, whether or not the screen ships yet):**
- Platform/foundational (§1): tenant scoping (`tenant_id` on every tenant-scoped table), Laravel Policies per entity (not CASL alone), Scheduler + queue worker setup — these aren't schema for a specific module, but every other Phase 1 item above assumes they exist
- Finance: Chart of Accounts (with the standard seed, §3.1), ledger posting service, `TaxCode` (with `Party.tax_residency_status`), `PaymentAllocation`, `ContractRetentionTerms` / `RetentionAccount` / `RetentionRelease` (with `early_release_reason`), `CreditNote`/`DebitNote` (with `InvoiceLine`, polymorphic across both and `Invoice`, plus VAT rounding rule), `CreditApproval` (with credit-limit enforcement and its row-lock), `Write-off`, `posting_date` on Invoice/Payment, `DocumentSequence` (per-tenant, §3.10, with migrating-client initialization, fiscal-year reset, and numbering format), `AccountingPeriod` (with the open-period-ambiguity resolution), `BankAccount` (minimal — moved from Phase 2, backs the Cash Position dashboard widget which is itself Phase 1), `OpeningBalanceBatch` (the migration mechanism, not just the prose description that used to stand in for it)
- CRM & Sales: Lead, `FeasibilityAssessment`, Quotation/SalesOrder, `SalesOrderLine` (Direct Sale and Manufacture-for-Sale had no line-item structure at all without this), `Delivery`, `SalesReturn`, `invoice_policy`, `BOQImportStaging` (the upload staging table, previously described in prose with no entity behind it)
- Inventory: Item/Category/UOM (with `valuation_method`), `stock_ledger` (with `warehouse_id` required, "Main Warehouse" seeded as the v1 default), availability computation
- Procurement: Demand Trigger (with reorder-level deduplication), PR (with `PurchaseRequisitionLine`), PO (with `PurchaseOrderLine`, `currency_id`/`exchange_rate`/FX gain-loss clearing, and the `partially_received` state, §5.2), GRN, QC, `LandedCost`, `RMReservation`, `Subcontract` (with `required_document_types`) / `ProgressClaim` (with `reversed` status), supplier `Payment` disbursements (with `settlement_exchange_rate`), post-acceptance supplier returns
- Projects: `Project` (with `cancelled` terminal state), `Milestone` (BOQ-linked, with `rework_required`), `VariationOrder`/`VariationOrderLine`/`VariationOrderReversal`, `Defect`, `AnalyticAccount` — tables exist even though the UI ships in Phase 2
- Cross-cutting: `AuditLog` (wired via model observers from day one, not phased)

Two items promoted into this list on review, moving out of what was originally scoped as backlog: **`CreditNote`/`DebitNote`** — a KRA-numbered invoice can't be corrected by a negative invoice or a bypassing journal entry, so once `DocumentSequence` makes invoice numbers legally meaningful, credit/debit notes stop being optional. **Minimal multi-currency (`currency_id`/`exchange_rate` on PO/GRN only)** — `LandedCost` was already Phase 1 and freight/duty/clearing on imports is routinely foreign-currency; this is the floor needed for that to mean anything, not full multi-currency reporting (§14 still has FX revaluation and multi-currency GL as backlog).

**Phase 1 screens** — everything above except Manufacturing, Labour & Resourcing, and Projects/Milestones UI, which get Phase 2 screens against tables that already exist. **The full standard financial report set moves into Phase 1 too (§10.1): Trial Balance, AR/AP Aging, Balance Sheet, Income Statement/P&L, General Ledger (Detail & Summary), Cash Flow Statement.** These aren't dashboard widgets — they're the statements a business and its auditor actually need, all derivable from tables that already exist in Phase 1, and none of them should be left implicit just because they're "obviously derivable." `ChartOfAccounts.account_type`/`is_contra` (§3.1) is the one small addition this requires.

**Phase 2 screens** — Manufacturing (BOM, Production Order, Processing FG), Labour & Resourcing, Projects & Milestones UI (including VariationOrder and Defect screens), `ApprovalLimit`, `Notification`, `ComplianceDocument`, **Fixed Assets & Plant/Equipment (§3.12) — full module: Asset, AssetComponent, AssetDepreciationEntry, AssetRevaluation, AssetDisposal, AssetAssignment, EquipmentHireContract, plus the Fixed Asset Register and Depreciation Schedule reports (§10.1) that pair with it — an auditor asking for the asset register is exactly as certain as them asking for the Trial Balance, so these ship with the module, not after it.** Scheduled early in Phase 2, same treatment as HR & Payroll — it doesn't block Phase 1's commercial/procurement/inventory core, but it directly affects the Balance Sheet (Fixed Assets and Accumulated Depreciation are real line items, not optional detail), so it shouldn't be left to drift to the end of Phase 2. **HR & Payroll (§3.11) — full module: Employee, EmploymentContract (with non-overlap enforcement), Timesheet, LeaveRequest, PayrollRun, Payslip, `FinalSettlement`/`LeaveEncashment`, P9A/P10 reports.** Placed in Phase 2 rather than Phase 1 because it has no hard dependency on the commercial/procurement/inventory core — but it's a full build in its own right, not an afterthought, and should be scheduled early in Phase 2 rather than last, given Kenyan formal-sector procurement treats payroll compliance as close to a checklist item.

**Phase 3** — live inventory board (real-time read layer over the stock ledger), PWA offline for site supervisors, M-Pesa STK Push/API integration, KRA iTax/TIMS/eTIMS filing submission, KRA/NSSF/SHIF statutory online filing API (the HR module itself and its P9A/P10 reports are Phase 2 — this is specifically the government-facing submission step)

**Site Supervisor connectivity gap between Phase 1 and Phase 3 PWA, addressed rather than left as three years of "write it on paper":** the offline PWA is genuinely Phase 3 work, but a site supervisor's core needs (log a GRN line, flag a Defect, record a QC fail, submit a Timesheet) can't just go unrecorded until then. Interim path: structured SMS/WhatsApp templates via the TalkSasa infrastructure already wired for ImaraPay/ImaraConnect — a fixed-format message (`GRN <po_number> <item_code> <qty>`) parsed into a staged, reviewable record, the same confirm-before-live pattern already established for `BOQImportStaging`. This isn't as good as the PWA, but it's real-time and structured, versus the alternative of paper-then-re-entry, which is functionally identical to not having a system at all for that data.

**Delivery concerns that aren't schema but determine whether the first client can actually go live:**
- **Opening balances migration** — a new client arrives with existing inventory, AR/AP, retention balances, projects mid-flight, and YTD payroll (for P9A/P10 continuity). Approach: **hybrid** — sub-ledger reconstruction for AR/AP/Stock (the things users query by counterparty or item, where aging and per-customer balances need to work from day one) plus a single opening `JournalEntry` for everything else. A pure journal-entry-only opening is simpler but breaks AR/AP aging until new invoices accumulate; full sub-ledger reconstruction of everything is more accurate but is its own project.
- **File storage** — Laravel's filesystem abstraction makes the actual choice a one-line config change, but it needs deciding before Phase 1 since it shapes deployment topology (persistent volume vs. object storage) and upload UX limits for BOQ imports. Given the Data Protection Act consideration below, an S3-compatible provider with a Kenya-adjacent or Africa region (DigitalOcean Spaces, or equivalent) is the reasonable default over bare local disk.
- **`LedgerPostingService` test coverage is non-negotiable, not optional discipline** — one test per row of the §7 posting table, round-trip tests (post → reverse → ledger nets to zero), and a Trial-Balance-nets-to-zero test after any sequence of operations. This is the single point every financial transaction flows through; a bug here is wrong on every financial statement, not just one screen. Worth stating explicitly because under delivery pressure, ledger tests are usually the first thing skipped.
- **The security baseline and RPO/RTO targets in §1.1 are resolved before the first client's data goes in, not after.** "Where are our backups and what's your recovery time" is a procurement-stage question, not a month-three question — it needs an answer before the contract is signed, and retrofitting it after real client data exists is a materially harder problem than building it in from the start. MFA for Finance/Admin, webhook signature verification, and file-upload validation are Phase 1 for the same reason — they're the controls around real money and real PII from day one, not hardening added once something goes wrong.
- **Performance targets and indexing discipline (§1.1) are a Phase 1 item, not a Phase 2 optimization pass.** You don't need to *tune* Phase 1, but every foreign key and every `(tenant_id, status)`/`(tenant_id, posting_date)` composite needs to be indexed from the first migration, and the response-time/report-generation targets need to exist as a number to measure against, not be discovered by user complaints.
- **Idempotency on inbound webhooks and health check endpoints (§1.1) ship with Phase 1**, even though M-Pesa/TalkSasa integration itself is Phase 3 — the idempotency-key handling needs to be a property of the webhook-receiving infrastructure from the start, not bolted onto each integration as it's added.

**Deliberately excluded, not just deferred:**
- **Document control / transmittals** — skipped per your call; this is tier-one main-contractor infrastructure and not a fit for the current client base. Revisit only if a specific engagement requires it.
- **WIP (percentage-of-completion revenue recognition)** — held back past Phase 3, not placed in it. WIP calculation needs trustworthy cost-to-complete data, and that data only becomes reliable once real projects have run through the AnalyticAccount/Retention/VO model for a while. Building it against an unproven cost model would produce numbers that look precise without being reliable — better to let the underlying cost tracking prove itself first.

**A handful of further UX conventions worth stating once, at varying depths — some are real product decisions, a few are deliberately left to whoever designs the actual screens:**
- **Bulk entry.** A 30-line construction invoice or PO entered one field at a time is a real adoption blocker, not a minor friction. - **First-run onboarding.** A new tenant's first login shouldn't be a dashboard of zeroes with no orientation — a first-run checklist (Chart of Accounts confirmed, users invited, warehouses set up, opening balances run) is a Phase 1 deliverable, kept brief here since the actual content is a product/CS artifact, not an architecture concern.
- **Form error recovery.** Losing a 40-line PO's data on a validation error is the kind of thing that costs disproportionate user goodwill — stated as a hard rule rather than left implicit: no multi-step form loses entered state on a server-side validation failure.
- **User training material.** Given this document's own read that Kenyan ERP adoption stalls on complexity (§9 above), short walkthroughs for the top daily workflows are a Phase 1 deliverable — not glamorous, and deliberately not specified further here, since it's a delivery artifact for whoever owns client onboarding, not a schema or process decision.

### 10.1 Standard Financial Reports

Dashboards above are interactive widgets; these are the formal statements a business — and its auditor — actually asks for. All are derived entirely from existing tables; none require new source-of-truth data. Named explicitly here because "trivially derivable" isn't the same as "actually specified," and a report nobody named tends to not get built.

**Parameter convention, stated once rather than left for each report screen to invent independently:** every point-in-time report (Balance Sheet, Fixed Asset Register) takes a single "as of" date, defaulting to the most recently `closed` `AccountingPeriod`; every period report (Income Statement, Cash Flow, GL Summary) takes a start/end date, defaulting to the current open period; management-facing dashboards (§10) default to "as of now," live. One convention, reused everywhere, rather than each report picking its own default.

| Report | Derived from | Phase |
|---|---|---|
| **Trial Balance** | `JournalLine` grouped by `account_id`, summed Dr/Cr as of a date — already Phase 1 (§8), included here for completeness | 1 |
| **AR Aging / AP Aging** | `Invoice`/`ProgressClaim.net_payable` less `PaymentAllocation` sums, bucketed by days overdue from `posting_date` — already Phase 1 (§8) | 1 |
| **Party Ledger (Counterparty Statement)** | Every `Invoice`/`CreditNote`/`DebitNote`/`Payment`/`PaymentAllocation` for one `Party`, in date order, with a running balance — the transaction-history view AR/AP Aging doesn't provide (aging shows outstanding amounts, not the history behind them). This is what an AP clerk reconciles a supplier statement against at month-end; without it named as its own report, that reconciliation has nowhere to happen. | 1 |
| **Balance Sheet** | `JournalLine` grouped by `ChartOfAccounts.account_type` (asset/liability/equity), net balance as of a date. Assets: Fixed Assets at Cost less Accumulated Depreciation, Inventory (per §6's valuation method), Accounts Receivable, Retention Receivable, WHT Receivable, Cash/Bank. Liabilities: Accounts Payable, Retention Payable, VAT Payable, the statutory payables (§3.11), Customer Advance, Net Pay Payable, Other Deductions Payable. Equity: Retained Earnings, Asset Revaluation Reserve. **Retained Earnings is computed at report time, never physically closed** — no `period_close` event exists or is needed: the figure is `Retained Earnings (Opening)` (§3.1, the migration plug) plus the running sum of every posted Revenue `JournalLine` less every posted Expense `JournalLine` from inception to the report date, the same "computed not stored" principle already used for stock valuation and accumulated depreciation elsewhere in this document. Revenue and Expense accounts are never zeroed out or swept at period-end — `AccountingPeriod.status = closed` (§3.10) only blocks *new* postings into that period, it doesn't trigger any posting of its own. This was previously undefined (the doc named the figure without saying how it's derived); resolved this way rather than by adding closing-entry machinery, since a computed aggregate is simpler, has no timing/ordering dependency on when "close" runs, and can't itself be wrong in a way a posted closing entry could be. **Performance note, not a Phase 1 concern but worth naming so it isn't rediscovered under pressure:** summing every Revenue/Expense `JournalLine` from inception is fine at Phase 1 volumes and within the 2-second report target (§1.1), but the General Ledger Summary report (above) already computes per-account opening/movement/closing per period — the natural place to cache period-level aggregates if this computation's cost ever grows enough to matter. | 1 |
| **Income Statement / P&L** | `JournalLine` grouped by `account_type` (revenue/expense) between two dates. | 1 |
| **Project P&L** | The same Income Statement query, filtered by `analytic_account_id` (§3.7) — **named as its own report row rather than left as an implied filter parameter**, since it's arguably the single most valuable report a construction client has: revenue minus every cost (materials, labour, subcontract, equipment) that touched one project. | 1 |
| **General Ledger — Detail** | Every `JournalLine` for one account within a period, in date order, with a running balance column. This is what `JournalEntry`/`JournalLine` *are* — the GL was never a separate model, just a query that was never named. | 1 |
| **General Ledger — Summary** | Opening balance, period movement (sum Dr, sum Cr), closing balance, per account, per period. | 1 |
| **Cash Flow Statement** | Not a trivial re-aggregation like the others — see the mechanism below. | 1 |
| **Fixed Asset Register** | One row per `Asset`: `asset_number`, `name`, `category`, `date_of_purchase`, `purchase_cost`, accumulated depreciation as of the report date (summed from `AssetDepreciationEntry`, same "computed not stored" principle as `stock_ledger`), net book value, `location_id`, `custodian_party_id`, `status`. This is specifically what an auditor requests and asks to tie back to the Balance Sheet's Fixed Assets line. | 2 (paired with §3.12) |
| **Depreciation Schedule** | Two views, not one: **Planned** — projected period-by-period depreciation from `Asset.purchase_cost`/`useful_life_years`/`depreciation_method`/`residual_value`, recalculated forward whenever a revaluation or lifespan change occurs. **Actual** — the posted `AssetDepreciationEntry` rows. Both matter because they diverge in practice (a revaluation resets the planned schedule; an actual run might be skipped or corrected) — showing only one view would hide exactly the kind of discrepancy an asset audit is looking for. | 2 (paired with §3.12) |

**Cash Flow Statement mechanism.** Unlike the Balance Sheet/P&L, this isn't a simple regroup-by-account-type — it needs a category (operating/investing/financing) that `ChartOfAccounts` doesn't carry. Rather than add a stored field to every `JournalLine` (another thing to keep in sync), the category is a **lookup keyed on `JournalEntry.eventType`**, computed at report time, applied only to `JournalLine` rows that actually hit a Cash/Bank account:

- **Operating:** `payment_received`, `payment_made` (supplier/subcontractor disbursement — see §3.4/§3.9's `Payment.direction = disbursement`, previously missing as an event entirely), `net_pay_disbursed`, `statutory_remittance`, `other_deductions_remitted`, `retention_released_client`, `retention_released_subcontractor` (when disbursed via cash rather than offset against AP)
- **Investing:** `asset_acquired` (only when it directly credits Cash/Bank rather than Accounts Payable — a credit purchase isn't a cash flow event until the *payment* against that AP happens, which is its own `payment_made` disbursement, correctly categorized separately), `asset_disposed` (the `sale_proceeds` portion, when received as cash rather than left as a debtor)
- **Financing:** `capital_movement` (all four `CapitalMovement` directions, §3.9 — a Phase 1-minimal entity added specifically because a first construction-SME client taking a loan or an owner injecting capital is a month-one event, not an eventual one). Full loan amortization, interest accrual automation, and cap-table management stay backlog (§14); this only ensures the Financing bucket isn't structurally empty from day one.

**Operational dependency, stated rather than assumed:** the Cash Flow Statement (and the Cash Position dashboard widget below) is only as complete as the `Payment` records that exist — if a client's accountant pays a supplier by bank transfer outside Imara and never records a `Payment`, that cash movement is invisible to both. This is inherent to not having a reconciled Banking module yet (§14); worth naming as an operational dependency, not a silent gap.

This only works correctly because the categorization is applied to individual Cash/Bank `JournalLine` rows, not to whole events — an asset bought on credit never appears until the cash actually moves, which is the economically correct behavior for a cash flow statement, not an approximation of one.

## 11. RBAC — initial role set

- **Sales** — Lead, Quotation, Feasibility Check
- **Procurement** — Demand Trigger, PR, PO, GRN, Supplier Performance
- **Warehouse** — Stock Ledger, QC disposition, Reservations
- **Finance** — Chart of Accounts, Journal Entries, Credit Approval, Payments
- **Project Manager** — Project, Milestone, Resource Assignment
- **Site Supervisor** — Project Utilization, Quality Sign Off, **and GRN creation for goods received directly at site** (mobile-first, candidate for Phase 3 offline PWA). Stated explicitly because site staff, not the warehouse, are routinely the ones physically present when a delivery arrives at a project site — if the Site Supervisor role can't create a GRN, either the doc is silently assuming a warehouse-clerk handshake workflow that was never specified, or materials sit unrecorded until someone from the office visits. Where a client's actual process *is* a site-to-warehouse handshake (site logs receipt informally, warehouse formalizes the GRN later), that's a valid alternative — but it's a client-specific configuration choice, not the default assumption.
- **HR Manager** — Employee, EmploymentContract, LeaveRequest approval, PayrollRun, Payslip, P9A/P10
- **Asset Manager** — Asset, AssetComponent, AssetRevaluation, AssetDisposal, AssetAssignment, EquipmentHireContract, ComplianceDocument. §3.12 and §3.10 introduced these without a role owning them; folding them into Finance would conflate custody/assignment (an operational concern) with posting (a financial one) the same way HR was kept separate from Finance despite HR ultimately feeding the ledger too.
- **Admin** — full access, role/permission management

**`Role` scoping, resolved rather than left implicit:** `Role` is **tenant-scoped** (`tenant_id`, per §3.1's tenancy rule — "no exceptions" means no exceptions, including reference-feeling tables), not a genuinely global shared catalog. In practice this changes nothing about how it's used day to day: every tenant gets the same nine roles above, seeded identically at provisioning time (part of the same onboarding sequence that seeds the Chart of Accounts) — same pattern already established for `ChartOfAccounts`, which is also per-tenant rows from one fixed standard list, not a shared global table. The reason this matters now rather than later: **Policy authorization in this system is role-*logic*-based, not permission-*matrix*-based** — "Finance can approve credit and post journal entries" is enforced by a Policy class's actual code checking the role, not by a stored, editable list of permissions that role happens to have. A tenant adding a tenth, custom role to their own tenant-scoped `Role` table wouldn't automatically gain any enforcement, because no Policy class exists yet that consults anything about that new role — the schema would accept the row, but nothing in the authorization layer would act on it. **If tenant-defined custom roles become a real requirement, that's a `Permission`/`RolePermission` layer and a rework of every Policy class to check a stored matrix instead of hardcoded logic — a genuinely separate, larger piece of work, correctly deferred to backlog (§14) rather than half-built now** by just adding `tenant_id` to `Role` and calling it customizable. Tenant-scoping `Role` today costs nothing and keeps the door open architecturally; building the permission-matrix system speculatively, before any client has actually asked for custom roles, would be over-building ahead of proven need — the same restraint this document applies to WIP accounting, full multi-currency, and the rest of §14's backlog.

## 12. Open Decisions

1. ~~Confirm "C.A" reading~~ — **Resolved: Check Availability**, confirmed in §2.2.
2. ~~Milestone billing granularity~~ — **Resolved by `invoice_policy` (§3.2)**: `on_milestone` fixes the amount at Milestone creation from the BOQ; if recalculation against actual utilization is wanted instead, that's a variant of the same field, not a schema question.
3. ~~Wastage variance threshold~~ — **Resolved: record-only, with alert escalation.** Blocking production is operationally hostile — by the time a foreman sees a variance figure, the material's already mixed and the waste already happened; a block just produces a workaround where someone else enters the transaction instead, and the data gets worse, not better. `BillOfMaterials.tolerance_pct` (§3.1) plus a `bom_variance_exceeded` Notification (§3.10) is the whole mechanism — record, alert, let a human decide. No configurable multi-threshold rule engine; a single tolerance per BOM is what's actually used.
4. ~~Multi-warehouse from day one, or single warehouse for v1?~~ — **Resolved: required from day one.** `warehouse_id` is mandatory on `stock_ledger` (§3.3), with a "Main Warehouse" seeded as the v1 default — construction sites are inherently multi-location (central warehouse, site, in-transit, quarantine), so single-warehouse was the wrong default to begin with.
5. ~~Should Direct Sale / Manufacture for Sale orders optionally attach to a Project~~ — **Lower-stakes**: `AnalyticAccount` (§3.7) handles per-project financial rollups independently of `sales_orders.project_id`, so this is a UI convenience decision, not a reporting-correctness one.
6. ~~Retention percentage and DLP duration~~ — **Resolved: pre-fill 5% / 12 months.** A configuration seed, not a schema change — `ContractRetentionTerms` stays per-contract (§3.9), this only sets what a new contract starts with. 5% is the conservative default (under-withholding is easier to correct upward later than chasing back money already held); 12 months matches FIDIC Red Book and most Kenyan government contracts, so the more-demanding case is the one that needs no adjustment. Both remain editable per-contract.
7. ~~Variation Order approval flow~~ — **Resolved: reuses `ApprovalLimit` (§3.10)**, thresholded by `amount_delta` rather than a bespoke chain — same mechanism already built for PR/PO, not a second approval system.
8. ~~BOQ → Milestone allocation granularity~~ — **Resolved in §3.7**: `boq_line_allocations` with `percentage_of_value` is the single primitive; section-level is a shorthand that expands to lines, not a separate mechanism.
9. ~~Payroll data visibility~~ — **Resolved: Finance gets read access to aggregate `JournalLine` postings only, never individual `Payslip` records.** `HR Manager` retains full `PayrollRun`/`Payslip` access. Finance's reconciliation need (does the payroll journal entry tie out?) is fully satisfied by the posted `JournalEntry` — gross pay, employer statutory cost, and net pay payable are all visible there at the aggregate level — and doesn't require seeing any individual's salary. Principle of least privilege wins over convenience here: salary data is inherently more sensitive than most entities in this system, and "Finance happens to also do reconciliation" isn't a strong enough reason to grant it. An employee's own `Payslip` remains visible to themselves via self-service, separately from either role.

## 15. Regulatory & Compliance Note

Imara holds employee PII (national ID, KRA PIN, NSSF/SHIF/HELB numbers, salary, bank details), customer/supplier PII, and subcontractor compliance documents. Kenya's **Data Protection Act 2019** applies — registration with the ODPC as a data controller/processor, data subject rights (access, correction, deletion), breach notification, and restrictions on cross-border transfer if hosted outside Kenya. This isn't a schema fix, but three decisions already in this document flow directly from it: **hosting region** (the S3-compatible file storage choice above should weigh Kenya/Africa-region hosting, not default to the cheapest US/EU region), **audit log contents** (`AuditLog`, §3.10, logs PII in `old_values`/`new_values` by nature — that's itself a DPA consideration, not just a security feature), and **retention/deletion policy** (financial records are correctly soft-deleted-only per §3.10, but a terminated employee has a right-to-erasure claim that a blanket "never hard-delete" policy doesn't accommodate — HR records likely need a different, shorter-than-financial retention rule). **The right-to-erasure mechanism itself, and its interaction with off-site backups, is now resolved in §1.1** rather than left as an open question — `Employee` PII anonymized in place, `Payslip` amounts retained under statutory record-keeping obligations, `AuditLog` identity references anonymized rather than deleted, and erasure against backups satisfied once pre-erasure backups age out of the retention window rather than promising something immutable backups can't actually provide. Not a full legal analysis — flagged here so it's a conscious decision during Phase 1 planning, not a discovery during a client's compliance review.

## Two-Year Outlook

Would building v20 as documented produce a system that holds for at least two years without a forced schema rework? **Yes** — the decisions that historically force ERP rewrites (wrong accounting model, missing financial controls, schema regrets) are the ones already resolved here: retention direction, VAT-on-retention, `PaymentAllocation`, reversal-only journal policy, valuation-method immutability, append-only stock ledger, `AuditLog`/`AccountingPeriod` from day one, Fixed Assets & Plant/Equipment tied into the Shadow Ledger regardless of client plant profile, statutory payables (and now WHT Receivable) that actually clear, a full standard financial report set (§10.1), an operational envelope with real RPO/RTO/security/performance targets (§1.1), a complete transaction lifecycle including its edge cases and race conditions (v13–v14), a foundation layer that actually exists (`Tenant`, `UserInvitation`, idempotency storage — v18) rather than being assumed, and a Kenya compliance layer present in the schema from Phase 1 even where the API integration is Phase 3. Five years is plausible on this schema without a rework; what changes after that is additive modules, not a replacement.

Two things could break the two-year runway, in order of likelihood — down from three, since client-shape mismatch is no longer a risk now that Fixed Assets & Plant/Equipment (§3.12) is built regardless of the first clients' plant profile:

1. **Data volume** — the computed-availability pattern (§6) starts to slow around 5M+ `stock_ledger` rows per tenant and 100+ concurrent users. Fixed with materialized views or a read replica for the availability board, not a schema change — a 3-5 year horizon for a mid-size contractor, not a two-year risk unless a client is unusually large.
2. **Unexpected feature demand** — unavoidable, but the cross-cutting primitives (`AuditLog`, `Notification`, `ApprovalLimit`, `AnalyticAccount`, `DocumentSequence`) are generic enough that most plausible additions (Daily Site Reports, HSE, Tendering, Banking, Budgeting — everything in §14) are new tables referencing existing entities, not changes to the core.

The practical framing: v20 isn't a version you upgrade *from* in two years, it's a version you build *around*, by adding modules.
